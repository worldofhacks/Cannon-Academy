## Context

The competitive frame, and one of the game's explicit child-safety guarantees: **rank is a
ratchet.** A loss costs a child nothing but time. Encoding that as a pure function with a test
is how the guarantee survives a day-5 refactor.

```ts
export function rankTierForWins(wins: number): number; // 0..4
export function rankForWins(wins: number): Rank; // catalog entry
export function advanceRank(currentTier: number, wins: number): number; // ratchet
export function rankByTier(tier: number): Rank;
```

- `rankTierForWins(w)` = the highest `rank.tier` whose `rank.minWins <= w`.
- `advanceRank(currentTier, wins)` = `max(currentTier, rankTierForWins(wins))`. It takes no
  `won` flag on purpose: there is no code path that can lower a tier.
- Tiers are numeric so the `leaderboard/{uid}` mirror orders correctly (ARCHITECTURE.md §5).

## Planning Decisions

- `locked-decision` — rank never decreases. PLAN.md states it twice.
- `proposed` — `advanceRank` deliberately has **no** parameter that could express a demotion.
  An API that cannot express the forbidden state is stronger than one that checks for it.
- `open-question` — the `minWins` value at each tier lives in `ranks.json` (T-006) and PLAN.md
  gives no numbers. This ticket depends only on their being non-negative and strictly
  increasing, which T-006's AC-7 guarantees.
- `proposed` — rank has no effect on matchmaking, payouts, or difficulty in this swarm. PLAN.md
  describes rank as "the competitive frame" and dates it day 4; the ladder's _consequences_
  (leaderboard mirror, rank-gated content) are out of scope.

## Acceptance Criteria

- **AC-1**: Given `wins = 0`, when `rankTierForWins` is called, then it returns `0` and
  `rankForWins(0).id` is `"cadet"`.
- **AC-2**: Given `wins` sweeping `0 … 500`, when `rankTierForWins` is called for each, then
  every result is an integer in `[0, 4]` and the sequence is non-decreasing.
- **AC-3**: Given each rank in the catalog, when `rankTierForWins(rank.minWins)` is called, then
  it returns exactly that rank's `tier` — the boundary win count promotes, inclusively.
- **AC-4**: Given each rank above `cadet`, when `rankTierForWins(rank.minWins - 1)` is called,
  then it returns `rank.tier - 1` — one win short does not promote.
- **AC-5**: Given a `wins` value greater than the highest `minWins`, when called, then it
  returns `4` (`fleet_legend`) and never a larger tier.
- **AC-6**: Given `advanceRank(3, 0)`, then it returns `3` — a player at Commodore with the win
  count reset stays at Commodore. Given `advanceRank(0, w)` where `w` promotes to tier 2, then
  it returns `2`.
- **AC-7**: Given `advanceRank(current, wins)` over 1,000 combinations of `current` in `[0, 4]`
  and `wins` in `[0, 500]`, then the result is always `>= current` and always `<= 4`.
- **AC-8**: Given a simulated career of 200 duels with an arbitrary seeded win/loss pattern in
  which `wins` only ever increases on a win and never changes on a loss, when the tier is
  advanced after each duel, then the tier sequence is non-decreasing and no loss ever changes
  the tier.
- **AC-9**: Given a negative `wins`, a non-integer `wins`, a negative `currentTier`, or a
  `currentTier` greater than `4`, when the relevant function is called, then it throws a
  `RangeError`.
- **AC-10**: Given `rankByTier(t)` for `t` in `[0, 4]`, then it returns the matching catalog
  rank; given `rankByTier(5)`, then it throws an `Error` naming the missing tier — never
  returns `undefined`.
- **AC-11**: Given every rank returned by any function here, when its `tier` is compared with
  its position in the catalog sorted by `tier`, then they match, and the id order is
  `cadet, ensign, captain, commodore, fleet_legend`.
