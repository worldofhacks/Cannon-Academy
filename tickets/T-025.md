## Context

`src/engine/questions/expr.ts` bounds AST height at `MAX_AST_DEPTH = 1024`, checked at every
construction site, so an over-long expression fails as `PARSE_ERROR` during parsing rather than
overflowing the stack during a walk. That satisfies T-002 AC-26 and is verified across nine
input shapes with no bypass.

**But the three walks — `checkNode`, `computeNumber`, `computeBoolean` — are still natively
recursive, so the cap is a _margin_, not a proof.** The T-002 code review measured the real
overflow point by lifting the cap in a scratch copy and bisecting at controlled stack sizes:

| stack                        | max evaluable chain | margin over the 1024 cap |
| ---------------------------- | ------------------- | ------------------------ |
| 4 MB (Node default)          | 18,756              | 18.3×                    |
| 1 MB (≈ browser main thread) | 3,521               | 3.4×                     |
| 0.5 MB (constrained worker)  | 1,569               | **1.5×**                 |

It also found the boundary is **run-dependent**, not merely host-dependent.

The margin holds everywhere measurable — breaching it needs a host stack under roughly 0.35 MB —
and reaching height 1024 requires an expression about 100× taller than any plausible template
(`floor(a/b)+c` is height 4). So this is robustness work, not a live defect.

**Why it is worth doing anyway:** this module runs inside T-007's rejection-sampling loop on
React Native (Hermes), a host whose stack budget this run has not measured. Converting the walks
to explicit-stack iteration removes host-dependence entirely and turns AC-26's guarantee from
"holds with a measured margin" into "holds by construction".

## Planning Decisions

- `proposed` — explicit-stack iteration for all three walks. The alternative (lowering
  `MAX_AST_DEPTH`) shrinks the margin problem without removing it, and costs legitimate headroom.
- `locked-decision` — **behaviour must not change.** All 335 frozen T-002 tests pass unmodified,
  including error-code identity and the left-to-right depth-first failure ordering that T-002's
  M-3 ruling depends on.

## Acceptance Criteria

- **AC-1**: Given the three walk functions, when the module is read, then none of them calls
  itself directly or mutually — traversal state lives in an explicit stack.
- **AC-2**: Given the full T-002 frozen suite (335 tests), when run against this implementation,
  then all pass unmodified, with no change to any thrown `code`.
- **AC-3**: Given an expression at exactly `MAX_AST_DEPTH`, when evaluated under a **0.5 MB**
  stack (`node --stack-size`), then it evaluates successfully rather than throwing `RangeError` —
  the case where the current 1.5× margin is thinnest.
- **AC-4**: Given expressions whose evaluation fails, when compared against the pre-change
  implementation over a shared corpus, then the reported error `code` is identical for every
  input — the left-to-right depth-first ordering is preserved exactly.
- **AC-5**: Given the evaluator's documented performance-relevant path (T-007 calls
  `evaluatePredicate` once per rejection-sampling candidate), when a realistic template expression
  is evaluated, then per-call time does not regress measurably against the recursive version.

## Test Plan

- Unit (deterministic): the frozen T-002 suite, unmodified, as the regression contract.
- Unit (deterministic): a source-level assertion that the walks are non-recursive, backed by an
  ESLint `no-restricted-syntax` rule rather than a text grep (see LESSONS.md L-016 — a text scan
  fails correct code on naming).
- Unit (deterministic): differential corpus comparing error codes before and after.
- Integration: none.

## Out of Scope

- Changing `MAX_AST_DEPTH`, the grammar, the whitelist, or any error code.
- Performance optimisation beyond not regressing.
- The recursive descent _parser_ — it is bounded at construction and is not the concern here.
