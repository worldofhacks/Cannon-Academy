## Context

Verified against the shipped catalogs:

```
starters:                         swivel_gun, culverin
port_sumwich unlocksCannons:      six_pounder, chain_shot, double_broadside
available after the first island: 5          duel tray capacity: 3
```

**Nothing in the engine or the design decides which three sail with you.** The design review
surfaced this; the code confirms it. By the Grandline a player holds up to ten.

This is pure engine logic — which cannons are _equipped_, given which are _owned_ — and it has no
home today. The screen that drives it is a design deliverable; this ticket is the rules beneath it.

## Planning Decisions

- `proposed` — the loadout is **explicit and persisted**, not derived. A player chooses; the choice
  survives relaunch. Deriving it (e.g. "the three most recently unlocked") is simpler but silently
  overwrites a child's decision the moment a chest drops a cannon — exactly the kind of invisible
  state change that makes a game feel unfair.
- `proposed` — an **auto-fill fallback** covers the pre-choice case: before a player has ever opened
  the loadout screen, the equipped set is the first `TRAY_CAPACITY` owned cannons in catalog order.
  A new player must never face an empty tray.
- `proposed` — `TRAY_CAPACITY` belongs in `tuning.ts` (ARCHITECTURE §4.3: every magic number, one
  file). It is **not** currently there — adding it is part of this ticket.
- `open-question` — whether the loadout may be changed mid-duel. Recommended **no**: it converts a
  strategic commitment into a menu, and PLAN.md's premise is that gun selection _is_ the strategy.
  Owner to confirm.
- `open-question` — whether a cannon whose skill sits above the player's grade band may be equipped.
  Recommended **yes** if owned; a harder gun is a legitimate stretch choice, and T-011's placement
  already gates what a player _owns_.

## Acceptance Criteria

- **AC-1**: Given a set of owned cannon ids and no explicit loadout, when the equipped set is
  requested, then it returns the first `TRAY_CAPACITY` owned cannons in catalog order.
- **AC-2**: Given an explicit loadout of exactly `TRAY_CAPACITY` owned cannons, then it is returned
  unchanged and in the player's chosen order.
- **AC-3**: Given an explicit loadout containing a cannon the player does not own, then it is
  rejected with a typed error naming the offending id — a stale saved loadout must never equip a
  cannon that was never earned.
- **AC-4**: Given an explicit loadout with more than `TRAY_CAPACITY` entries, or with duplicates,
  then it is rejected with a typed error.
- **AC-5**: Given a player who owns **fewer** than `TRAY_CAPACITY` cannons, then the equipped set is
  all of them — a K-1 player with two owned cannons gets two, not an error and not a padded tray.
- **AC-6**: Given a newly owned cannon and an existing full loadout, then the loadout is
  **unchanged** — acquiring a cannon never silently re-equips.
- **AC-7**: Given any player owning at least one cannon, then the equipped set is never empty.
- **AC-8**: Given the module, then it is pure: no `Math.random()`, no `Date`, no I/O, and identical
  inputs always produce an identical equipped set.
