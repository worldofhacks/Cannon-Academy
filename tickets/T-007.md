## Context

The hot path of the whole game: turn a pool of templates plus a PRNG state into one rendered,
four-choice `Question` and the advanced PRNG state. Everything it does is deterministic given
its inputs — this is what makes both the T-019 golden suite and the T-024 replay proof possible.

**Signature:**

```ts
export function generateQuestion(input: {
  readonly templates: readonly Template[]; // pool, pre-filtered to one skill by the caller
  readonly recentTemplateIds: readonly string[]; // most-recent-first
  readonly rng: Rng;
}): readonly [Question, Rng];
```

**Algorithm, in order — each step is an AC below:**

1. **Eligibility.** Exclude any template whose id appears in the first `RECENT_TEMPLATE_WINDOW`
   entries of `recentTemplateIds`. If that empties the pool, fall back to the unfiltered pool
   (a small skill must still produce questions). If the unfiltered pool is empty, throw
   `QuestionGenerationError` with `code` `NO_TEMPLATE`.
2. **Pick** one eligible template with `pick(rng, eligible)`.
3. **Rejection-sample params.** For each param key in **lexicographically ascending order**,
   draw `nextInt(rng, lo, hi)` inclusive. Evaluate every entry in `constraints` with
   `evaluatePredicate`; if any is false, discard the whole draw and retry. Up to
   `MAX_PARAM_SAMPLE_ATTEMPTS` (100) attempts; on exhaustion throw `QuestionGenerationError`
   with `code` `CONSTRAINTS_UNSATISFIED`, naming the template id.
4. **Answer.** `evaluateNumber(template.answerExpr, params)`.
5. **Distractors.** `buildDistractors` from T-005 (pure — consumes no PRNG).
6. **Render.** Replace every `{name}` token in `template.text` with the sampled value of that
   param. Every token must name a declared param and every param need not be used. Any `{` or
   `}` remaining after substitution throws `QuestionGenerationError` with `code`
   `INVALID_QUESTION`.
7. **Assemble and shuffle.** Build the four choices as `{ value, label }` with
   `label = String(value)`, shuffle with `shuffle(rng, choices)`, and set `correctIndex` to the
   post-shuffle index of the answer.

Consumes: `Rng`/`pick`/`nextInt`/`shuffle` (T-001), `evaluateNumber`/`evaluatePredicate` (T-002),
`Template`/`Question`/`QuestionGenerationError` (T-003), `MAX_PARAM_SAMPLE_ATTEMPTS`/
`RECENT_TEMPLATE_WINDOW`/`CHOICE_COUNT` (T-004), `buildDistractors` (T-005).

## Planning Decisions

- `locked-decision` (2026-07-28) — **the contract is that the returned question satisfies
  `assertQuestion`'s invariants, not that the generator observably calls it.** `types.ts` documents
  that "T-007 calls `assertQuestion`", and the review rightly noted the ticket never required that
  call. Requiring it would mean a test that spies on a module, freezing an implementation detail in a
  suite meant to constrain behaviour — and `assertQuestion`'s checks are a subset of what the criteria
  already assert on the output, so the spy would buy nothing. `types.ts` is frozen and outside this
  ticket's `file_scopes`; its wording describes intent and is left for the ticket that owns it.
- `locked-decision` — the seven-step order above and the 100-attempt bound come straight from
  ARCHITECTURE.md §4.1.
- `proposed` — params are sampled in lexicographically ascending key order. ARCHITECTURE.md does
  not say, but _some_ order must be fixed or the same seed produces different questions on
  different JSON key orderings, and replay breaks. Sorted keys are stable against re-authoring.
- `proposed` — the recency filter degrades gracefully to the unfiltered pool rather than
  throwing. A hard failure here would make a small skill unplayable; T-004's AC-4 already keeps
  `RECENT_TEMPLATE_WINDOW` below the per-skill template floor so this path is a safety net.
- `proposed` — `recentTemplateIds` is passed in, not held in module state. Session history is
  the caller's (the duel reducer's / drill's) responsibility; the generator stays pure.
- `proposed` — the caller pre-filters `templates` to the intended skill. This keeps the generator
  independent of the template catalog (T-014/15/16) and so free of any dependency cycle.
- `proposed` — `label = String(value)`. Fraction and picture-choice presentation
  (PLAN.md §The armory: "tap-the-picture choice") is a rendering concern for
  `src/components/**`, which is out of this swarm's scope.

## Acceptance Criteria

- **AC-1**: Given a single-template pool, the same `rng`, and the same `recentTemplateIds`, when
  `generateQuestion` is called 50 times, then all 50 returned `Question` values are deeply equal
  and all 50 returned `Rng` values are equal.
- **AC-2**: Given two different seeds and a pool of 8 templates, when 200 questions are generated
  from each, then the two sequences of `templateId` values are not identical.
- **AC-3**: Given a pool whose ids are `t1..t8`, `RECENT_TEMPLATE_WINDOW = w`, and
  `recentTemplateIds` listing the `w` most recent ids, when 500 questions are generated (each
  time prepending the previous id to `recentTemplateIds`), then no generated `templateId` ever
  appears in the first `w` entries of the `recentTemplateIds` passed to that call.
- **AC-4**: Given a pool of exactly 1 template and a `recentTemplateIds` containing that id, when
  called, then it returns a question from that template rather than throwing — the recency filter
  degrades to the unfiltered pool.
- **AC-5**: Given an empty `templates` array, when called, then it throws
  `QuestionGenerationError` with `code` `NO_TEMPLATE`. Conversely, given **any** non-empty pool
  containing at least one usable template, `NO_TEMPLATE` is **never** thrown — including when the
  recency window would empty the eligible pool, which step 1 handles by falling back to the
  unfiltered pool.
  _Negative half added 2026-07-28._ The criterion bounded only when `NO_TEMPLATE` **must** fire, so
  an implementation that threw it eagerly — say, whenever recency filtering emptied the pool, instead
  of falling back — satisfied it. A criterion that names only the failure case constrains nothing
  about the success case.
- **AC-6**: Given a template with `params { a: [1, 9], b: [1, 9] }` and constraint
  `"a + b <= 10"`, when 1,000 questions are generated, then every sampled `a` and `b` is an
  integer in `[1, 9]` inclusive and every pair satisfies `a + b <= 10`.
- **AC-7**: Given a template with an unsatisfiable constraint (`params { a: [1, 2] }`,
  `constraints ["a > 100"]`), when called, then it throws `QuestionGenerationError` with `code`
  `CONSTRAINTS_UNSATISFIED` and a message containing the template id. This must hold **for every
  seed swept, asserting the error type and `code` on each** — not merely that something was
  thrown. An implementation that returns the typed error at one seed and a bare `RangeError`
  everywhere else is a live mutant that passed the first draft of this suite (LESSONS.md L-034).
- **AC-8**: Given a template with no `constraints` key at all, when called, then it succeeds and
  the sampled params lie inside their declared inclusive ranges.
- **AC-9**: Given a template with `params { a: [4, 4] }`, when called, then `a` is `4` on every
  attempt and the call succeeds on the first sample.
- **AC-10**: Given `text: "{a} + {b} = ?"` and sampled `{ a: 3, b: 5 }`, when called, then
  `question.text` is exactly `"3 + 5 = ?"` and contains no `{` or `}`.
- **AC-11**: Given `text: "{a} + {z} = ?"` where `z` is not a declared param, when called, then
  it throws `QuestionGenerationError` with `code` `INVALID_QUESTION`, and **`cause` is absent**
  (`undefined`). As with AC-7, the error type, `code`, and absent `cause` must be asserted **on
  every seed swept**, not just at one fixture.
  _`cause` clause added 2026-07-28._ Render failures are not expression failures. A round-3 review
  proved a live mutant that ran render before distractors and attached a **fabricated** `ExprError`
  as `cause`, which satisfied AC-21's `instanceof` check while violating step order — and AC-11 did
  not notice, because it never looked at `cause`.
- **AC-12**: Given any successful call, when the result is inspected, then `choices.length`
  equals `CHOICE_COUNT` (4), `correctIndex` is an integer in `[0, 3]`,
  `choices[correctIndex].value` equals `evaluateNumber(template.answerExpr, question.params)`,
  and all four `value`s are pairwise distinct. The `Question` must also carry
  `skill === template.skill`, `templateId === template.id`, and `label === String(value)` on
  every choice — all three are required by step 7 and by `Question`'s own type, and a generator
  hardcoding any of them passed the first draft of this suite.
- **AC-13**: Given 2,000 questions generated from one template across incrementing seeds, when
  the distribution of `correctIndex` is measured, then each of the four indices occurs at least
  350 and at most 650 times — the correct answer is not biased toward a fixed slot.
- **AC-14**: Given any successful call, when the returned `Rng` is compared to the input `Rng`,
  then its `state` differs; and when the returned `Rng` is fed back in, the second call's draws
  **continue the stream rather than restarting it** — the resulting question and returned state
  are exactly those the frozen PRNG produces from the returned state, and differ from what a
  reset to the original seed would produce.
  _Amended 2026-07-28._ This criterion previously required that the second call "produces a
  different parameter draw". That is **measurably false for legal inputs**: consecutive draws may
  coincide by chance. Measured independently twice — one parameter over `[1,9]` repeats on
  **63 of 500 seeds** (12.6%, against a theoretical 55.6%⁻¹ ≈ 11.1%), two parameters over `[1,12]`
  on 4 of 500. A per-call inequality would flake on roughly one seed in eight. Assert continuation,
  which is what the intent was; never assert inequality of two consecutive draws.
- **AC-15**: Given a template with `isWordProblem: true` and `readAloud: true`, when called,
  then `question.isWordProblem` is `true` and `question.readAloud` is `true`; given a template
  omitting both keys, then both are `false` on the `Question` (absent means false, never
  `undefined`).
- **AC-16**: Given a template whose distractors cannot be resolved, when called, then the
  `QuestionGenerationError` with `code` `DISTRACTOR_FAILURE` from T-005 propagates unchanged.
- **AC-17**: Given a template declaring its params in a non-alphabetical order with disjoint
  ranges (for example `b` before `a`), when called, then the values drawn are exactly those the
  frozen `nextInt` yields when the keys are consumed in **ascending code-point order — plain
  `Array.prototype.sort()` with no comparator, never `localeCompare`** —
  an `Object.keys()` implementation must fail. And given the four assembled choices, the array
  handed to `shuffle` is `[answer, ...distractors]`, **answer first**, so `correctIndex` is the
  post-shuffle position of that element. Both orderings change the question a given seed
  produces, so T-024's replay proof depends on each; neither was pinned by any criterion before
  this amendment.
  _Collation named 2026-07-28._ "Lexicographically ascending" alone was ambiguous, and AC-19 made
  the ambiguity reachable by admitting mixed-case keys: over `['a','B','_x','Total']` the two
  candidate readings genuinely disagree — code point gives `["A_1b2","B","Total","_x","a",…]`,
  `localeCompare` gives `["_x","a","A_1b2","a1","B",…]` — while agreeing on every lowercase single
  letter, which is every key in the real catalog **and both keys in this criterion's own fixture**.
  A `localeCompare` implementation therefore passed the whole suite until a mixed-case fixture was
  added. Code point order is the ruling because it is `sort()`'s default, needs no locale data at
  all, and so cannot drift with a platform's ICU version — the property a replay proof rests on.
- **AC-18**: Given a schema-valid template with `params: {}` and a constant `answerExpr`, when
  called, then it **succeeds**: step 3 performs zero `nextInt` draws and steps 4 through 7 proceed
  normally. A generator that rejects a zero-parameter template as `INVALID_QUESTION` passed the
  first draft of this suite, because no fixture reached that branch.
- **AC-19**: Given a template, every key of `params` matches `[A-Za-z_][A-Za-z0-9_]*`, and every
  `{name}` token in `text` naming a declared param is substituted. Param keys are expression
  variables — T-002's grammar is `IDENT := [A-Za-z_][A-Za-z0-9_]*`, so a key outside that
  pattern can never appear in `answerExpr` or a constraint. `templateSchema` currently permits
  arbitrary string keys; **T-034 narrows it to match**, and until that lands this criterion is the
  binding statement of the contract.

- **AC-20**: Given a template carrying a **schema-valid but malformed expression** in any of the
  three sites that get evaluated — a `constraints` entry (step 3), `answerExpr` (step 4), or a
  declared `distractors` entry (step 5) — for example `"a +"`, when called, then it throws
  `QuestionGenerationError` with `code` `INVALID_QUESTION`, naming the template id, and carrying as
  its `cause` an `ExprError` whose **`code` and `message` match** the error the frozen site
  evaluator throws for that same expression and params (measured independently via
  `evaluatePredicate` / `evaluateNumber` / `buildDistractors`). A fabricated `ExprError` — any
  `instanceof` match that is not the diagnosis those modules produce — fails this criterion.
  **No `ExprError` escapes the generator**, from any site.
  _Added 2026-07-28 on the round-2 test-design review, which proved this live._ A perfectly ordinary
  implementation that calls `evaluateNumber` / `evaluatePredicate` / `buildDistractors` directly and
  does not translate their errors **passed all 72 tests and typechecked clean**, because every fixture
  in the suite held an evaluable expression. It nonetheless breaks DoD-5's promise that every failure
  path throws a typed `QuestionGenerationError` with a `code`.
  The reachability is the point: `templateSchema` types `answerExpr` as `z.string()`, so `"a +"` is
  schema-valid and reaches the generator unchallenged. **This resolves an apparent conflict rather
  than creating one.** `buildDistractors` documents `@throws {ExprError} unchanged`, and it stays
  exactly as it is — it is a frozen module outside this ticket's `file_scopes`. The translation
  happens at **this** module's boundary, because the generator is what the app and T-020 call, and
  DoD-5's entire value to a caller is that one error type covers every failure. `cause` is required
  so the content-authoring bug stays diagnosable; `Error.cause` is assignable at this project's
  ES2022 target, so satisfying it needs no change to the frozen `types.ts`.
- **AC-21**: Given a template that would fail at **two** different steps, when called, then the error
  reported is the one belonging to the **earliest step in the documented order** — the generator does
  not reorder its steps to prefer one diagnosis. Covering at least: a template with both an
  unsatisfiable constraint (step 3) and a malformed `answerExpr` (step 4) reports
  `CONSTRAINTS_UNSATISFIED`, and one with both a malformed declared distractor (step 5) and an
  unrenderable `text` token (step 6) reports the distractor failure. Both of the latter carry
  `INVALID_QUESTION`, so the code alone cannot separate them — distinguish by `cause`:
  - step-5 diagnosis: an `ExprError` matching AC-20's identity rule (same `code`/`message` as
    `buildDistractors` throws for that expression), **not** merely `instanceof ExprError`
  - step-6 render diagnosis: `cause` is **absent** — assert this on a pure-render fixture too
    (AC-11), not only by implication from the dual-failure case
    _Added 2026-07-28; identity rule tightened same day._ Round-3 review proved live
    (`m3-render-first-fake-cause`, 81/81): render-before-distractors + fabricated `ExprError` cause
    defeated a presence-only `instanceof` check. Control without the fake cause died on exactly one
    test — so AC-21 partially bit and still let the competent cheat through.
