## Context

The heart of the product, and the one module where a bug traps a child in a broken fight.
`duelReducer(state, event): DuelState` — pure, synchronous, total, and never throwing on a
well-formed state/event pair.

**Transition table (complete — anything not listed is a no-op):**

| from | event | to | effects |
|---|---|---|---|
| `countdown` | `ANIMATION_DONE` | `playerChoose` | `turnToken++` |
| `playerChoose` | `CANNON_SELECTED` | `reload` | validate `cannonId ∈ playerLoadout`; generate the question from `templatesBySkill[cannon.skill]` with the state's `rng`; store `timerMs = cannon.timerMs`; push the template id onto `recentTemplateIds` |
| `reload` | `ANSWER_CHOSEN` | `resolvePlayer` | grade against `question.correctIndex`; `resolveShot`; apply damage; append `ActionLogEntry{actor:'player'}`; update `tally` |
| `reload` | `TIMER_EXPIRED` | `resolvePlayer` | identical to a wrong `ANSWER_CHOSEN` with `elapsedMs = timerMs` |
| `resolvePlayer` | `ANIMATION_DONE` | `victory` \| `defeat` \| `rivalTurn` | terminal checks first; otherwise `turnToken++` |
| `rivalTurn` | `RIVAL_ACTION` | `resolveRival` | `resolveShot` for the rival's cannon and volley; apply damage to `playerHull`; append `ActionLogEntry{actor:'rival'}` |
| `resolveRival` | `ANIMATION_DONE` | `victory` \| `defeat` \| `playerChoose` | terminal checks first; otherwise `volleyNumber++`, `turnToken++` |
| `victory`, `defeat` | *any* | — | no-op |

**Terminal check, applied identically at both `ANIMATION_DONE` exits:** if `enemyHull <= 0` →
`victory`; else if `playerHull <= 0` → `defeat`; else continue.

**No-op semantics:** an out-of-phase event returns **the same state object reference** (`===`).
Not a copy, not a clone — reference equality, so a React store can skip the re-render and a test
can assert it cheaply.

**Damage application** goes through T-008's `resolveShot`, which advances the PRNG exactly once
per shot including misfires. `playerHull` and `enemyHull` are clamped at `0` on the way down and
never exceed their maxima.

## Planning Decisions

- `locked-decision` — the eight phases, five events, and the no-op rule are ARCHITECTURE.md §4.2.
- `locked-decision` — the reducer is pure and synchronous. All async lives in the store driver.
- `proposed` — `turnToken` increments on entry into `playerChoose` and into `rivalTurn`: the two
  phases where the machine is waiting on an external actor, which is precisely what the driver's
  stale-promise discard compares against.
- `proposed` — `TIMER_EXPIRED` is graded as a wrong answer with `elapsedMs = timerMs`, so a
  volatile gun recoils on a timeout exactly as it does on a wrong tap. PLAN.md's MVP checklist
  requires "time out a question and see the misfire" and treats it as a miss.
- `proposed` — an out-of-phase event returns the identical reference rather than a structurally
  equal copy. Reference equality is a stronger, cheaper contract.
- `proposed` — a `CANNON_SELECTED` naming a cannon outside `playerLoadout` is a **no-op**, not a
  throw. It is reachable from a racing UI (a double-tap during a phase change), which is exactly
  what the no-op rule exists for.
- `proposed` — a missing or empty template pool for the selected cannon's skill **throws**
  `QuestionGenerationError` with `code` `NO_TEMPLATE`. That is a configuration bug, not a race,
  and swallowing it would produce a duel with no question.
- `proposed` — the reducer records per-skill tallies in `DuelTally.bySkill` but never calls
  `mastery.ts`. Half-rate mastery is applied by the store from the finished `DuelResult`,
  keeping progression out of the combat machine.
- `locked-decision` — **this ticket does not depend on T-018.** The reducer is synchronous and
  consumes `RIVAL_ACTION` events carrying a `RivalVolley`, which lives in T-013's
  `duel/types.ts`. Nothing in the transition table touches the `Opponent` interface; that is the
  store driver's job, and the driver is out of scope. An earlier draft declared `T-018` here; it
  was a phantom edge that cost a full wave and proved nothing. The real async↔sync seam is proven
  where it can be exercised at scale — T-024 drives its 2,000-duel fuzz through
  `createScriptedOpponent` and `createBotOpponent`, which also gives all of
  `src/engine/opponents/**` a genuine in-scope consumer.
- `open-question` — **Reliable vs Standard on a miss.** Inherited from T-008: both currently lose
  the turn and deal no self-damage. If `reliable` is meant to grant a re-answer, that is a new
  transition and needs a written rule first.

## Acceptance Criteria

- **AC-1**: Given a fresh `countdown` state, when `ANIMATION_DONE` is dispatched, then the phase
  is `playerChoose` and `turnToken` increased by exactly `1`.
- **AC-2**: Given a `playerChoose` state, when `CANNON_SELECTED` names a cannon in
  `playerLoadout`, then the phase is `reload`, `cannonId` matches, `question` has four distinct
  choices, `timerMs` equals that cannon's `timerMs`, `recentTemplateIds[0]` is the new question's
  `templateId`, and the state's `rng` has advanced.
- **AC-3**: Given a `playerChoose` state, when `CANNON_SELECTED` names a cannon **not** in
  `playerLoadout`, then the returned state is the identical object reference (`===`).
- **AC-4**: Given a `reload` state, when `ANSWER_CHOSEN` supplies `question.correctIndex` with
  `elapsedMs` at 90% of the timer, then the phase is `resolvePlayer`, `outcome.kind` is
  `"volley"`, `enemyHull` decreased by `outcome.damageToEnemy`, `tally.correctAnswers` and
  `tally.totalAnswers` each increased by `1`, and `actionLog` gained one entry with
  `actor: 'player'`, `correct: true`, and the supplied `elapsedMs`.
- **AC-5**: Given a `reload` state on a **volatile** cannon, when `ANSWER_CHOSEN` supplies a wrong
  index, then `outcome.kind` is `"misfire"`, `enemyHull` is unchanged, `playerHull` decreased by
  that cannon's `recoilDamage`, `tally.totalAnswers` increased by `1`, `tally.correctAnswers` is
  unchanged, and the log entry has `correct: false`.
- **AC-6**: Given a `reload` state on a **reliable** cannon, when a wrong answer is given, then
  `playerHull` and `enemyHull` are both unchanged and the phase is `resolvePlayer`.
- **AC-7**: Given a `reload` state, when `TIMER_EXPIRED` is dispatched, then the resulting state
  is deeply equal to the state produced by an `ANSWER_CHOSEN` with a wrong index and
  `elapsedMs === timerMs` — except that the recorded `elapsedMs` is `timerMs` in both.
- **AC-8**: Given a `reload` state, when `ANSWER_CHOSEN` carries a `choiceIndex` outside
  `[0, 3]` or a negative `elapsedMs`, then the returned state is the identical object reference.
- **AC-9**: Given a `reload` state, when `ANSWER_CHOSEN` supplies the correct index with
  `elapsedMs` below `PERFECT_SHOT_TIMER_FRACTION * timerMs`, then `outcome.perfectShot` is
  `true`, `tally.perfectShots` increased by `1`, and `outcome.ballCount` is
  `BASE_BALLS_PER_VOLLEY + 1`.
- **AC-10**: Given a `resolvePlayer` state whose volley brought `enemyHull` to `<= 0`, when
  `ANIMATION_DONE` is dispatched, then the phase is `victory`, `result.won` is `true`,
  `result.tally` equals the state's tally, `result.volleys` equals `volleyNumber`, and
  `enemyHull` is exactly `0` (clamped, never negative).
- **AC-11**: Given a `resolvePlayer` state whose volatile recoil brought `playerHull` to `<= 0`,
  when `ANIMATION_DONE` is dispatched, then the phase is `defeat`, `result.won` is `false`, and
  `playerHull` is exactly `0`.
- **AC-12**: Given a `resolvePlayer` state with both hulls above `0`, when `ANIMATION_DONE` is
  dispatched, then the phase is `rivalTurn`, `turnToken` increased by `1`, and `volleyNumber` is
  unchanged.
- **AC-13**: Given a `rivalTurn` state, when `RIVAL_ACTION` carries a correct volley, then the
  phase is `resolveRival`, `playerHull` decreased by `damageToPlayer`, `actionLog` gained one
  entry with `actor: 'rival'` and the volley's `cannonId`/`correct`/`elapsedMs`, and
  `tally.totalAnswers` is **unchanged** — the tally counts the player's answers only.
- **AC-14**: Given a `rivalTurn` state, when `RIVAL_ACTION` names a cannon outside
  `rivalLoadout`, then the returned state is the identical object reference.
- **AC-15**: Given a `resolveRival` state with both hulls above `0`, when `ANIMATION_DONE` is
  dispatched, then the phase is `playerChoose`, `volleyNumber` increased by `1`, and `turnToken`
  increased by `1`.
- **AC-16**: Given each of the eight phases, when every event type that is not in that phase's
  row of the transition table is dispatched, then every result is the identical object
  reference — a `8 × 5` exhaustive matrix.
- **AC-17**: Given a `victory` or `defeat` state, when any of the five events is dispatched, then
  the returned state is the identical object reference — a finished duel is frozen.
- **AC-18**: Given a full scripted duel — countdown, four correct player volleys against
  `port_sumwich`'s enemy hull, with rival volleys between — when driven to `victory`, then
  `actionLog` alternates `player`, `rival`, `player`, … in dispatch order, contains one entry per
  volley by each actor, and `result.volleys` equals the number of player volleys.
- **AC-19**: Given the same `DuelConfig` and the same ordered event sequence, when the duel is
  replayed 20 times, then all 20 final states are deeply equal — the machine is fully
  deterministic given its seed and its inputs.
- **AC-20**: Given any reachable state produced during AC-18's scripted duel, when round-tripped
  through `JSON.parse(JSON.stringify(state))` and then fed the next event, then the resulting
  state is deeply equal to the un-round-tripped path — a duel survives a mid-duel kill and
  relaunch (PLAN.md MVP checklist).
- **AC-21**: Given a `playerChoose` state whose `templatesBySkill` has no entry for the selected
  cannon's skill, when `CANNON_SELECTED` is dispatched, then it throws
  `QuestionGenerationError` with `code` `NO_TEMPLATE` — a configuration bug fails loudly.
- **AC-22**: Given any transition in the table, when the input state is compared before and
  after, then the input object and every array it holds are unmutated — the reducer only ever
  returns new objects.
- **AC-23**: Given a `reload` state whose `enemyHull` is `5` and whose cannon rolls more than `5`
  damage, when a correct `ANSWER_CHOSEN` is dispatched, then the resulting **`resolvePlayer`**
  state — before any `ANIMATION_DONE` — already has `enemyHull === 0`, never a negative value.
  Symmetrically, given a `rivalTurn` state with `playerHull` of `3` and an incoming volley
  exceeding it, the resulting `resolveRival` state has `playerHull === 0`. Clamping happens where
  damage is applied, not at the terminal transition.
- **AC-24**: Given the test file for this ticket, when its phase and event enumerations are
  inspected, then they are **hardcoded literal arrays**, not derived from `DUEL_PHASES` or the
  `DuelEvent` union. T-022 adds a sixth event in wave 6; a derived enumeration would silently
  change AC-16's matrix rather than failing loudly.

## Test Plan

- Unit (deterministic): AC-1, AC-2, AC-12, AC-15 — the happy-path transitions and turn-token
  stamping.
- Unit (deterministic): AC-4, AC-5, AC-6, AC-7, AC-9 — the answer matrix required by
  ARCHITECTURE.md §9.2: correct, wrong on volatile (backfire), wrong on reliable, timeout, and
  perfect shot.
- Unit (deterministic): AC-10, AC-11, AC-23 — victory and defeat paths with hull clamping, plus
  the intermediate-phase overkill clamp. AC-10/AC-11 check the terminal states; AC-23 checks the
  state that actually applies the damage, which is where a missing clamp would live.
- Unit (deterministic): AC-24 — a structural check on this ticket's own test file, so wave 6's
  Double-Shot extension patches these tests instead of superseding them.
- Unit (deterministic): AC-3, AC-8, AC-14, AC-16, AC-17 — the no-op contract, including the
  exhaustive phase × event matrix and the frozen-terminal rule. AC-16 is the anti-soft-lock test.
- Unit (deterministic): AC-13, AC-18 — rival turns and action-log ordering, which is the input
  T-023's replay consumes.
- Unit (deterministic): AC-19, AC-20, AC-22 — determinism, serialisability across a live duel,
  and non-mutation.
- Unit (deterministic): AC-21 — the loud configuration failure.
- Eval: none. The reducer is a pure function; the opponent is a state machine, not a model.
