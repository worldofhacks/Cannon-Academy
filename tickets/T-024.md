## Context

`.tdd-swarm/posture.md` names two catastrophe classes. T-019 guards the first ("the game teaches
wrong math"). This ticket guards the second: **a duel state machine that soft-locks a child
mid-fight.**

```ts
export interface InvariantViolation {
  readonly code: InvariantCode;
  readonly detail: string;
}
export type InvariantCode =
  | 'NEGATIVE_HULL' | 'HULL_ABOVE_MAX' | 'NEGATIVE_TALLY' | 'TALLY_INCONSISTENT'
  | 'INVALID_PHASE' | 'INVALID_VOLLEY_NUMBER' | 'INVALID_TURN_TOKEN'
  | 'MALFORMED_QUESTION' | 'MALFORMED_ACTION_LOG' | 'TERMINAL_RESULT_MISMATCH';

export function checkDuelInvariants(state: DuelState): readonly InvariantViolation[];
export function assertDuelInvariants(state: DuelState): void;   // throws on the first violation
export function isStuck(state: DuelState): boolean;             // non-terminal and no event advances it
```

**The invariant set** — each maps to exactly one `InvariantCode`:

1. `0 <= playerHull <= PLAYER_HULL` and `0 <= enemyHull <= enemyMaxHull`.
2. Every `tally` counter is a non-negative integer; `correctAnswers <= totalAnswers`;
   `perfectShots <= correctAnswers`; every `bySkill` entry has `correct <= attempts`, both
   non-negative integers; and `sum(bySkill.attempts) === tally.totalAnswers`.
3. `phase` is a member of `DUEL_PHASES`.
4. `volleyNumber >= 1` and is an integer; `turnToken >= 0` and is an integer.
5. In `reload`: `question.choices.length === CHOICE_COUNT`, all four values distinct,
   `correctIndex` in `[0, 3]`, and `timerMs > 0`.
6. Every `ActionLogEntry` has a `cannonId` present in the relevant loadout, a boolean `correct`,
   and a finite non-negative `elapsedMs`.
7. In `victory`: `enemyHull === 0` and `result.won === true`. In `defeat`: `playerHull === 0`
   and `result.won === false`. In both: `result.tally` deep-equals `state.tally`.

**`isStuck(state)`** is `true` when the state is non-terminal and *every* member of `DuelEvent`
(constructed with valid payloads for that state's loadouts and question) returns the identical
state reference. A `true` result is exactly the soft-lock a child would experience.

## Planning Decisions

- `proposed` — invariants live in shipped `src/engine/` code, not only in a test file, so the
  hidden `app/dev.tsx` screen can surface violations during a live playtest and a future
  server-side validator can reuse them. ARCHITECTURE.md §9.2 asks for the fuzz; making the
  predicate a first-class export costs nothing and buys both.
- `proposed` — `checkDuelInvariants` returns **all** violations; `assertDuelInvariants` throws on
  the first. A fuzz failure that reports every broken invariant at once is far faster to diagnose.
- `proposed` — the fuzz driver builds streams from the *declared* event union with valid payloads,
  including deliberately out-of-phase events, since the no-op rule is one of the things under
  test. Payloads are drawn from T-001's seeded PRNG so any failure is reproducible from its seed —
  the failing seed must be printed in the assertion message.
- `proposed` — **the fuzz driver sources its rival volleys from the real `Opponent`
  implementations**, awaiting `chooseAction`/`produceAnswer` from `createScriptedOpponent`
  (T-018) and `createBotOpponent` (T-021) and feeding the results in as `RIVAL_ACTION` events.
  This is deliberate and load-bearing for two reasons. First, it is the only place in this
  swarm's scope where the async `Opponent` ↔ synchronous reducer seam ARCHITECTURE.md §4.2
  spends four paragraphs on is actually exercised — the store driver that normally owns it is out
  of scope. Second, it gives every module under `src/engine/opponents/**` a genuine in-scope
  consumer, satisfying the substituted reachability requirement in `.tdd-swarm/posture.md`
  ("an orphan that nothing imports and no test drives is still a finding") rather than leaving
  four files tested only in isolation. It costs no extra wave: T-024 already sits behind T-022.
- `proposed` — the fuzz asserts **termination**: from a valid start, a stream containing enough
  well-formed events always reaches `victory` or `defeat` within a bounded number of dispatches.
  A machine that never finishes is a soft-lock even if no invariant is technically violated.
- `proposed` — "never negative coins" from ARCHITECTURE.md §9.2 is covered by T-009's AC-12; the
  duel state holds no coins. Noted so the requirement is not silently dropped.

## Acceptance Criteria

- **AC-1**: Given a state constructed by `createDuelState`, when `checkDuelInvariants` is called,
  then it returns an empty array.
- **AC-2**: Given a state hand-mutated to `playerHull: -1`, when checked, then the result
  contains exactly one violation with `code` `NEGATIVE_HULL` whose `detail` names the field and
  the value. Likewise `enemyHull: -1`.
- **AC-3**: Given a state hand-mutated to `enemyHull: enemyMaxHull + 1`, when checked, then the
  result contains a violation with `code` `HULL_ABOVE_MAX`.
- **AC-4**: Given a state whose `tally.correctAnswers` exceeds `tally.totalAnswers`, or whose
  `perfectShots` exceeds `correctAnswers`, or whose `bySkill` attempts do not sum to
  `totalAnswers`, when checked, then each produces a violation with `code` `TALLY_INCONSISTENT`;
  and a negative counter produces `NEGATIVE_TALLY`.
- **AC-5**: Given a `reload` state whose question has three choices, or two equal choice values,
  or a `correctIndex` of `4`, or `timerMs: 0`, when checked, then each produces a violation with
  `code` `MALFORMED_QUESTION`.
- **AC-6**: Given a `victory` state whose `enemyHull` is `5`, or whose `result.won` is `false`,
  or whose `result.tally` differs from `state.tally`, when checked, then each produces a
  violation with `code` `TERMINAL_RESULT_MISMATCH`.
- **AC-7**: Given an action log entry with a negative `elapsedMs` or a `cannonId` outside both
  loadouts, when checked, then it produces a violation with `code` `MALFORMED_ACTION_LOG`.
- **AC-8**: Given a state with three simultaneous violations, when `checkDuelInvariants` is
  called, then all three are returned; and when `assertDuelInvariants` is called, then it throws
  an `Error` whose message contains the first violation's `code` and `detail`.
- **AC-9**: Given every non-terminal phase reachable in a normal duel, when `isStuck` is called,
  then it returns `false`; and given a `victory` or `defeat` state, then it returns `false`
  (terminal is finished, not stuck).
- **AC-10**: Given 2,000 seeded fuzz duels, each dispatching up to 500 pseudo-randomly chosen
  well-formed events — including out-of-phase ones — when `checkDuelInvariants` is run after
  **every** dispatch, then no violation is ever reported. On failure the assertion message must
  include the seed and the dispatch index.
- **AC-11**: Given the same 2,000 fuzz duels, when `isStuck` is evaluated after every dispatch,
  then it is `false` at every non-terminal step.
- **AC-12**: Given the same 2,000 fuzz duels, when the reducer is dispatched, then it never
  throws for any well-formed event and any reachable state.
- **AC-13**: Given 500 seeded fuzz duels driven only by well-formed **in-phase** events, when
  each is run, then every one reaches `victory` or `defeat` within 400 dispatches — the machine
  always terminates.
- **AC-14**: Given the fuzz, when out-of-phase events are dispatched, then every one returns the
  identical state reference, and the count of such dispatches in a 2,000-duel run is greater than
  zero — proving the out-of-phase path was actually exercised and not merely never generated.
- **AC-15**: Given any state visited during the fuzz, when round-tripped through
  `JSON.parse(JSON.stringify(state))`, then `checkDuelInvariants` returns the same result for
  both — invariants hold across serialisation.
- **AC-16**: Given 500 seeded fuzz duels whose every rival volley is produced by awaiting
  `createScriptedOpponent`'s `chooseAction` then `produceAnswer` (T-018) and dispatching the
  combined `RivalVolley` as a `RIVAL_ACTION` event, then every duel reaches a terminal phase,
  `checkDuelInvariants` reports nothing at any step, and no promise resolves after its duel has
  terminated. This is the async `Opponent` ↔ synchronous reducer seam of ARCHITECTURE.md §4.2,
  exercised end to end.
- **AC-17**: Given 500 seeded fuzz duels whose rival volleys come from `createBotOpponent`
  (T-021) at a fixed accuracy and a fixed seed, then every duel reaches a terminal phase with no
  invariant violation; and re-running the identical setup reproduces the same terminal state
  exactly — a seeded bot driving a seeded reducer is fully deterministic end to end.
- **AC-18**: Given the two opponent-driven suites above, when the set of `src/engine/opponents/**`
  exports they touch is inspected, then `Opponent`, `createScriptedOpponent`,
  `createBotOpponent`, and at least one `mercy.ts` export are each executed at least once — no
  module in that directory is reachable only from its own unit tests.

## Test Plan

- Unit (deterministic): AC-1 … AC-9 — one targeted violation per `InvariantCode`, built by
  hand-mutating a valid state, plus the multi-violation and `isStuck` behaviour. These are what
  make the fuzz's silence meaningful: a checker that reports nothing on a broken state would
  otherwise pass AC-10 trivially.
- Unit (deterministic, seeded): AC-10, AC-11, AC-12, AC-14, AC-15 — the ARCHITECTURE.md §9.2
  invariant fuzz: 2,000 seeded duels × up to 500 events, checked after every dispatch, with
  coverage assertions so the out-of-phase branch is provably exercised. Deterministic despite the
  name — every stream comes from T-001's seeded PRNG.
- Unit (deterministic, seeded): AC-13 — termination under in-phase streams.
- Integration (deterministic, seeded): AC-16, AC-17, AC-18 — 1,000 duels driven through the real
  `Opponent` implementations. These are the only tests in the swarm that compose the async
  opponent seam with the synchronous reducer, and the only in-scope consumer of
  `src/engine/opponents/**`. Despite awaiting promises they are fully deterministic: every
  opponent resolves immediately (T-018 AC-8) and draws only from a seeded PRNG.
- Eval: none. Nothing here is sampled from a model; "fuzz" means seeded pseudo-random input to a
  pure function, and the "bot" is a seeded state machine.
