## Context

`templateSchema` declares `params: z.record(paramRangeSchema)`, which accepts **any** string as a
param key. T-002's expression grammar is `IDENT := [A-Za-z_][A-Za-z0-9_]*`, so a key outside that
pattern — `"a-b"`, `"2x"`, `""` — can never be referenced from `answerExpr` or from a constraint.
Such a key is therefore authorable, schema-valid, and unusable for the one purpose params exist
for.

The T-007 test-design review surfaced this: that ticket's render oracle only substitutes
identifier-shaped tokens, which is the right behaviour but was, at the time, **narrower than the
schema it validates against**. T-007's AC-19 now states the contract; this ticket makes the schema
agree, so the two cannot drift.

This is [[L-009]]'s shape. The catalogs are authored by a different ticket than the one owning the
schema, so an author who types a key the evaluator cannot see gets no error — just a param that
silently never resolves.

## Planning Decisions

- `locked-decision` — the pattern is exactly T-002's `IDENT`, `^[A-Za-z_][A-Za-z0-9_]*$`. It is
  not re-derived here; it is imported from the grammar that has to consume it, so a change to one
  cannot leave the other behind.
- `proposed` — reject at the schema boundary rather than at generation time. A malformed key is a
  content-authoring error, and the whole point of validating catalogs at load is that the failure
  arrives with the file name attached rather than mid-duel.
- `proposed` — this is a **narrowing** of a shipped schema. Every template in `src/content/**`
  today must be confirmed to already satisfy it, so the change is a no-op for existing content and
  a guard against future content. If any shipped template violates it, that is a content bug this
  ticket surfaces rather than accommodates.

## Acceptance Criteria

- **AC-1**: Given a template whose `params` keys all match `^[A-Za-z_][A-Za-z0-9_]*$`, when parsed
  by `templateSchema`, then it parses successfully and the keys are unchanged.
- **AC-2**: Given a template with a param key that does not match the pattern — covering at least
  a hyphen (`"a-b"`), a leading digit (`"2x"`), the empty string, a space (`"a b"`), and a dot
  (`"a.b"`) — when parsed, then parsing **fails** with an error naming the offending key.
- **AC-3**: Given every template in the shipped content catalogs, when parsed under the narrowed
  schema, then all of them still parse — the narrowing is a no-op for existing content.
- **AC-4**: Given the pattern used by the schema and T-002's identifier grammar, when compared,
  then they accept the same set of strings. The test asserts this over a shared corpus of
  candidate keys, so the two definitions cannot drift apart silently.

## Test Plan

- Unit (deterministic): AC-1, AC-2 — the accept and reject sets, with the reject cases enumerated
  rather than sampled, since the rejection set is what L-009 says a validator spec must state.
- Unit (deterministic): AC-3 — parse the real catalogs and assert no regression.
- Unit (deterministic): AC-4 — the drift check against T-002's grammar.
