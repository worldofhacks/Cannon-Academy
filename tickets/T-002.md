## Context

Question templates express their answer and their validity conditions as short strings over the
template's parameters:

```ts
params: { a: [1, 9], b: [1, 9] }
constraints: ["a + b <= 20", "a >= b"]
answerExpr: "a + b"
distractors: ["a + b + 1", "a + b - 1", "a * b"]
```

Something must turn those strings into numbers and booleans. **It must not be `eval()`,
`new Function()`, or any dynamic code construction** — this code path is fed by bundled content
today, but the module is a permanent attack and correctness surface, and a parser is cheap.

This is a self-contained tokenise → Pratt/recursive-descent parse → evaluate module with a
closed grammar and a whitelisted function set. It has no dependencies and is consumed by T-005
(distractors) and T-007 (generator).

**Grammar (complete — reject anything outside it):**

```
expr        := or
or          := and ( "||" and )*
and         := compare ( "&&" compare )*
compare     := sum ( ( "==" | "!=" | "<=" | ">=" | "<" | ">" ) sum )?
sum         := product ( ( "+" | "-" ) product )*
product     := unary ( ( "*" | "/" | "%" ) unary )*
unary       := ( "-" )? primary
primary     := NUMBER | IDENT | IDENT "(" args ")" | "(" expr ")"
args        := expr ( "," expr )*
NUMBER      := digits ( "." digits )?
IDENT       := [A-Za-z_][A-Za-z0-9_]*
```

Whitelisted functions, exactly these: `abs(x)`, `min(x, y)`, `max(x, y)`, `floor(x)`,
`ceil(x)`, `gcd(x, y)`.

## Planning Decisions

- `locked-decision` — no `eval` / `new Function` / dynamic code (ARCHITECTURE.md §4.1 says
  "tiny safe evaluator"; a child-facing math engine must not execute content as code).
- `proposed` — the function whitelist above. ARCHITECTURE.md gives no list; `gcd` and `floor`
  are included because fraction and division templates (T-016) need divisibility and reduction
  constraints. Adding a function later is a one-line change plus a test.
- `proposed` — `/` is real division returning a possibly-fractional `number`. Templates that
  need integer results must assert divisibility in `constraints` (e.g. `"a % b == 0"`). This
  keeps the evaluator honest instead of silently truncating and teaching wrong math.
- `proposed` — booleans are not first-class values; `evaluatePredicate` requires the expression
  to produce a boolean at top level, and `evaluateNumber` requires a number. Mixing is an error.

## Acceptance Criteria

- **AC-1**: Given the source file `src/engine/questions/expr.ts`, when its text is read, then it
  contains none of the substrings `eval(`, `new Function`, `Function(`, `setTimeout`,
  `setInterval`, or `import(`. **This scan is secondary defence, not the authoritative guard** —
  a substring scan is defeated by aliasing (`const F = Function; F(src)`) or computed access
  (`globalThis['ev' + 'al']`). **ESLint is NOT authoritative either** — this was claimed in an
  earlier revision of this ticket and is factually wrong. Measured against the repo's real
  config over eight spellings, `no-eval`/`no-implied-eval`/`no-new-func` caught **3 of 8**: they
  match the bindings literally named `eval` and `Function` and do not follow an alias, a computed
  member access, or reflection. `Reflect.construct(Function, [...])`,
  `Object.getPrototypeOf(function(){}).constructor(src)`, `const F = Function; F(src)`,
  `globalThis['ev'+'al'](src)`, and `setTimeout(stringVar, 0)` all pass lint silently.
  A complete evaluator built on `Reflect.construct` passed **229/229 frozen tests, `tsc` exit 0,
  and `eslint` exit 0** — see `.tdd-swarm/reports/T-002-test-design-review.md`.
- **AC-21**: Given the module is imported and evaluated with every route to dynamic code
  construction poisoned — `globalThis.Function`, `globalThis.eval`, `Reflect.construct` called
  with `Function`, and the `constructor` getter on `Function.prototype` — then no route is ever
  reached, at import time or at call time, while `evaluateNumber` and `evaluatePredicate` still
  return correct results. **This behavioural trap is the authoritative guard**; the AC-1 text
  scan and the ESLint rules are both secondary defence and are kept.
  _(Added by the orchestrator 2026-07-28. Obtaining the `Function` constructor requires the
  global binding, `<anyFunction>.constructor`, `Reflect` over one of those, or `eval` — trapping
  all four closes every route the reviewer could construct. Poisoning must happen BEFORE import
  so an init-time cached reference is also caught. Verified: passes against an honest
  recursive-descent parser, fails against the `Reflect.construct` implementation.
  Lessons L-001 and L-007 — a guard never observed blocking the thing it names is not a guard.)_
- **AC-2**: Given `evaluateNumber("a + b * c", { a: 2, b: 3, c: 4 })`, then it returns `14`
  (precedence), and given `evaluateNumber("(a + b) * c", { a: 2, b: 3, c: 4 })`, then it
  returns `20` (parentheses).
- **AC-3**: Given `evaluateNumber` with `{ a: 7, b: 2 }`, then `"a - b"` returns `5`,
  `"a * b"` returns `14`, `"a / b"` returns `3.5`, `"a % b"` returns `1`, and `"-a"` returns `-7`.
- **AC-4**: Given `evaluateNumber("a - b - c", { a: 10, b: 3, c: 2 })`, then it returns `5`
  (left associativity), and given `evaluateNumber("a / b / c", { a: 12, b: 3, c: 2 })`, then it
  returns `2`.
- **AC-5**: Given `evaluateNumber` with whitelisted calls, then `"abs(0 - 5)"` returns `5`,
  `"min(a, b)"` with `{a:3,b:9}` returns `3`, `"max(a, b)"` with `{a:3,b:9}` returns `9`,
  `"floor(a / b)"` with `{a:7,b:2}` returns `3`, `"ceil(a / b)"` with `{a:7,b:2}` returns `4`,
  and `"gcd(a, b)"` with `{a:12,b:18}` returns `6`.
- **AC-6**: Given `evaluatePredicate("a + b <= 20", { a: 9, b: 9 })`, then it returns `true`;
  given `{ a: 15, b: 9 }`, then it returns `false`.
- **AC-7**: Given `evaluatePredicate` with `{ a: 5, b: 5 }`, then `"a == b"` is `true`,
  `"a != b"` is `false`, `"a < b"` is `false`, `"a <= b"` is `true`, `"a > b"` is `false`, and
  `"a >= b"` is `true`.
- **AC-8**: Given `evaluatePredicate("a > 0 && b > 0 || a == 0", { a: 0, b: 0 })`, then it
  returns `true` (`&&` binds tighter than `||`).
- **AC-9**: Given `evaluateNumber("a + z", { a: 1 })` where `z` is not in the environment, then
  it throws an `ExprError` whose `code` is `UNKNOWN_IDENTIFIER` and whose message names `z`.
- **AC-10**: Given `evaluateNumber("foo(a)", { a: 1 })`, then it throws an `ExprError` with
  `code` `UNKNOWN_FUNCTION`; given `evaluateNumber("min(a)", { a: 1 })`, then it throws an
  `ExprError` with `code` `ARITY_MISMATCH`.
- **AC-11**: Given a malformed input — each of `"a +"`, `"(a + b"`, `"a ** b"`, `""`, `"a b"`,
  `"a $ b"` — then `evaluateNumber` throws an `ExprError` with `code` `PARSE_ERROR`.
- **AC-12**: Given `evaluateNumber("a / b", { a: 1, b: 0 })` or `"a % b"` with `b = 0`, then it
  throws an `ExprError` with `code` `DIVISION_BY_ZERO` — it never returns `Infinity` or `NaN`.
- **AC-13**: Given `evaluateNumber("a > b", { a: 2, b: 1 })`, then it throws an `ExprError` with
  `code` `TYPE_MISMATCH`; given `evaluatePredicate("a + b", { a: 1, b: 1 })`, then it throws an
  `ExprError` with `code` `TYPE_MISMATCH`.
- **AC-14**: Given the same expression string and the same environment, when evaluated 100
  times, then every result is identical — evaluation is pure and holds no cross-call state.
- **AC-15**: Given an expression nested more deeply than the parser's depth limit (e.g. 200
  nested parentheses), then it throws an `ExprError` with `code` `PARSE_ERROR` rather than
  overflowing the stack.
- **AC-16**: Given `"a % b"` with a **negative left operand** (`{a:-7,b:2}`), then it returns
  `-1` — JavaScript remainder semantics, where the sign follows the dividend — not `1`
  (mathematical modulo). Given `{a:7,b:-2}` it returns `1`.
  _(Orchestrator 2026-07-27. Was unspecified and matters directly: T-016 asserts divisibility
  via `"a % b == 0"`, and that idiom is correct under either convention, so the cheaper and
  less surprising choice is the language's own. A template needing true modulo writes
  `((a % b) + b) % b`.)_
- **AC-17**: Given `"gcd(a, b)"`, then it operates on absolute values — `{a:-12,b:18}` returns
  `6`, `{a:12,b:-18}` returns `6` — and `{a:0,b:5}` returns `5`, `{a:0,b:0}` returns `0`.
  _(Orchestrator 2026-07-27. Was unspecified; zero and negative arguments are reachable from
  constraint expressions and would otherwise be implementation-defined or hang.)_
- **AC-18**: Given a whitelisted function called with **zero arguments** (`"abs()"`), then it
  throws `PARSE_ERROR`, not `ARITY_MISMATCH`.
  _(Orchestrator 2026-07-27, resolving a genuine contradiction the Test Agent surfaced rather
  than guessed at: the grammar's `args := expr ( "," expr )*` requires at least one argument,
  so a zero-argument call never reaches the arity check. The grammar is declared complete and
  authoritative, so it wins. `ARITY_MISMATCH` remains correct for one-too-few or one-too-many.)_
- **AC-19**: Given the module's exports, then `ExprErrorCode` is a **type-only** export — a
  union of the string-literal codes — and `ExprError` is a runtime class extending `Error`
  carrying a `code: ExprErrorCode`. Importing `ExprErrorCode` as a value is a compile error.
  _(Orchestrator 2026-07-27. The DoD required exporting it without saying whether it was a type
  or a runtime value; the two are not interchangeable at the import site, so consumers in
  T-005/T-007 would have had to guess.)_
- **AC-20**: Given an expression nested **16 levels** deep, then it evaluates successfully.
- **AC-24**: Given `evaluatePredicate("b == 0 || z > 0", { b: 0 })` where `z` is **not** in the
  environment, then it throws `UNKNOWN_IDENTIFIER` — short-circuiting suppresses
  `DIVISION_BY_ZERO` but does **not** suppress an unknown identifier. Every identifier appearing
  anywhere in the expression must resolve against the environment, whether or not its branch is
  evaluated.
  _(Added by the orchestrator 2026-07-28, resolving the residual ambiguity the Test Agent
  flagged rather than invented. Rationale: identifier resolution is a STATIC check, like the type
  check AC-23 already makes static; only genuinely value-dependent failures — division by zero —
  are suppressed by short-circuiting. The alternative reading is more JS-like but strictly worse
  here: a typo'd parameter in a constraint (`a % b == 0 || zz > 1`) would sit undetected in a
  content catalog for as long as its branch happens to be short-circuited, and T-019's 1,000-sample
  sweep cannot guarantee it is ever evaluated. Constraints are hand-authored content, so the
  evaluator should fail loudly on a name that cannot exist rather than silently skip it.)_
- **AC-25**: Given any expression whose evaluation would produce or consume a **non-finite
  number** — a numeric literal too large to represent (`"9" * 309` → `Infinity`), an arithmetic
  result that overflows (`"9"*400 + " - " + "9"*400` → `NaN`, or `a * a` with `a = 1e200`), or a
  non-finite value supplied in the environment (`{ a: Infinity }`, `{ a: NaN }`) — then it throws
  an `ExprError` with `code` `NON_FINITE_VALUE`. `evaluateNumber` never returns `Infinity`,
  `-Infinity`, or `NaN`, and no non-finite value is ever passed to a whitelisted function.
  **`ExprErrorCode` becomes a seven-member union**; the frozen `Exact<>` assertion must be
  updated to match.
  _(Added by the orchestrator 2026-07-28. This closes a **Critical**: `gcd` loops forever on a
  non-finite argument, because `(NaN, NaN)` is a fixed point of the Euclid loop. Reproduced by
  the code review and independently by me — `gcd("9"×400, 2)` hangs **with an empty environment**,
  so a content literal alone reaches it; `gcd(a,b)` with `a = Infinity` hangs too. T-007 calls
  `evaluatePredicate` once per candidate inside a rejection-sampling loop, so this freezes the app
  with no error, no stack trace, and no recovery. AC-17's own rationale said the alternative was
  "implementation-defined **or hang**" — it then closed zero and negative and left the case that
  actually hangs. The DoD already promised "never returns `Infinity` or `NaN`"; this makes the
  promise real at both boundaries — inputs and results — rather than only for `/` and `%` by zero.
  A distinct code rather than overloading `TYPE_MISMATCH` so T-007 can tell "bad template" from
  "bad parameters".)_
- **AC-26**: Given any input, however long or deeply chained, **no `RangeError` or stack overflow
  escapes the public API** — every failure is an `ExprError`. In particular a flat operator chain
  (`"1" + "+1".repeat(n)` for large `n`, and the `&&`/`||` equivalents) throws `PARSE_ERROR`, not
  `RangeError`. The limit must be **deterministic** — a documented bound on input size or AST
  depth — not whatever depth the host's stack happens to reach. Expressions of realistic length
  (at least 200 terms) must still evaluate.
  _(Added by the orchestrator 2026-07-28. `MAX_NESTING_DEPTH` counts only paren and call nesting;
  the binary productions fold **iteratively**, so the counter never sees an operator chain — yet
  the resulting left-deep AST is walked with native recursion. AC-15's five tests all use
  `"(".repeat(n)` or `"abs(".repeat(n)`, so the suite was blind to the other shape of the same
  threat. The threshold is host-dependent: the code review bisected it at 4,562 terms, I measured
  a `RangeError` at 4,000 on the same file — which is exactly why the bound must be deterministic
  rather than emergent. This also falsifies the implementer's "100,000 … never a RangeError"
  measurement, which swept parens and calls only.)_
- **AC-22**: Given a name that is a real own-property of the built-in `Math` object but is NOT on
  the declared whitelist — `sqrt`, `round`, `pow`, `sign`, `trunc`, `log`, `hypot`, `cbrt`,
  `random` — when called with either one or two arguments, then it throws `UNKNOWN_FUNCTION`.
  _(Added by the orchestrator 2026-07-28. The whitelist is declared "exactly these", but every
  negative test used a name that is NOT an own property of `Math`, so an evaluator resolving
  calls as `hasOwnProperty.call(Math, name) ? Math[name] : ...` passed all thirteen AC-10 tests
  and 229/229 overall — silently exposing `pow`, `log`, `cbrt`, `atan2` and friends. Two waves
  later a template author could write `round(a / b)` in an `answerExpr` and it would work, drifting
  the contract with nothing recording it; worse, `log`/`cbrt`/`pow` produce irrational values that
  are not tappable answers in a K-5 game. Both arities are required so a length-based arity check
  cannot convert the failure into `ARITY_MISMATCH`. L-009: a criterion listing only accept cases
  is satisfied by an implementation that accepts everything.)_
- **AC-23**: Given `evaluatePredicate("b == 0 || a % b == 0", { a: 5, b: 0 })`, then it returns
  `true`; given `evaluatePredicate("b != 0 && a % b == 0", { a: 5, b: 0 })`, then it returns
  `false` — `&&` and `||` **short-circuit**, and a right operand that is not evaluated cannot
  raise `DIVISION_BY_ZERO`. A short-circuited operand is still **type-checked**: given
  `evaluatePredicate("b == 0 || a", { a: 5, b: 0 })`, then it throws `TYPE_MISMATCH`.
  _(Added by the orchestrator 2026-07-28. Short-circuit behaviour was unspecified and both
  conventions passed 229/229. They disagree on exactly the divide-by-zero guard a template author
  would naturally write, and T-007 calls `evaluatePredicate` per candidate during rejection
  sampling — under eager evaluation a guarded constraint THROWS on a candidate it was written to
  reject, turning an ordinary rejection into a generator crash against a module frozen two waves
  earlier. Resolved to the host language's semantics per L-010, consistent with the AC-16 ruling.)_
  _(Orchestrator 2026-07-27, adopting the Test Agent's inference as an explicit criterion. AC-15
  alone is satisfied by a depth limit of 2, which would reject legitimate templates while
  passing the suite — the L-006 failure mode. This pins a usable floor without dictating the
  exact limit.)_
