## Context

Question templates express their answer and their validity conditions as short strings over the
template's parameters:

```ts
params: { a: [1, 9], b: [1, 9] }
constraints: ["a + b <= 20", "a >= b"]
answerExpr: "a + b"
distractors: ["a + b + 1", "a + b - 1", "a * b"]
```

Something must turn those strings into numbers and booleans. **It must not be `eval()`,
`new Function()`, or any dynamic code construction** — this code path is fed by bundled content
today, but the module is a permanent attack and correctness surface, and a parser is cheap.

This is a self-contained tokenise → Pratt/recursive-descent parse → evaluate module with a
closed grammar and a whitelisted function set. It has no dependencies and is consumed by T-005
(distractors) and T-007 (generator).

**Grammar (complete — reject anything outside it):**

```
expr        := or
or          := and ( "||" and )*
and         := compare ( "&&" compare )*
compare     := sum ( ( "==" | "!=" | "<=" | ">=" | "<" | ">" ) sum )?
sum         := product ( ( "+" | "-" ) product )*
product     := unary ( ( "*" | "/" | "%" ) unary )*
unary       := ( "-" )? primary
primary     := NUMBER | IDENT | IDENT "(" args ")" | "(" expr ")"
args        := expr ( "," expr )*
NUMBER      := digits ( "." digits )?
IDENT       := [A-Za-z_][A-Za-z0-9_]*
```

Whitelisted functions, exactly these: `abs(x)`, `min(x, y)`, `max(x, y)`, `floor(x)`,
`ceil(x)`, `gcd(x, y)`.

## Planning Decisions

- `locked-decision` — no `eval` / `new Function` / dynamic code (ARCHITECTURE.md §4.1 says
  "tiny safe evaluator"; a child-facing math engine must not execute content as code).
- `proposed` — the function whitelist above. ARCHITECTURE.md gives no list; `gcd` and `floor`
  are included because fraction and division templates (T-016) need divisibility and reduction
  constraints. Adding a function later is a one-line change plus a test.
- `proposed` — `/` is real division returning a possibly-fractional `number`. Templates that
  need integer results must assert divisibility in `constraints` (e.g. `"a % b == 0"`). This
  keeps the evaluator honest instead of silently truncating and teaching wrong math.
- `proposed` — booleans are not first-class values; `evaluatePredicate` requires the expression
  to produce a boolean at top level, and `evaluateNumber` requires a number. Mixing is an error.

## Acceptance Criteria

- **AC-1**: Given the source file `src/engine/questions/expr.ts`, when its text is read, then it
  contains none of the substrings `eval(`, `new Function`, `Function(`, `setTimeout`,
  `setInterval`, or `import(`. **This scan is secondary defence, not the authoritative guard** —
  a substring scan is defeated by aliasing (`const F = Function; F(src)`) or computed access
  (`globalThis['ev' + 'al']`). The authoritative guard is ESLint, which matches identifier
  *references* rather than text. **Orchestrator action required before this ticket is dispatched:**
  add `no-eval`, `no-implied-eval`, and `no-new-func` to the `src/engine/**` + `src/content/**`
  block in `eslint.config.js` (they are not in `js.configs.recommended`), and prove them firing
  on a synthetic violation per lesson L-001. Keep the scan: it costs nothing and catches the
  spelling a lint rule's option set happens to miss.
- **AC-2**: Given `evaluateNumber("a + b * c", { a: 2, b: 3, c: 4 })`, then it returns `14`
  (precedence), and given `evaluateNumber("(a + b) * c", { a: 2, b: 3, c: 4 })`, then it
  returns `20` (parentheses).
- **AC-3**: Given `evaluateNumber` with `{ a: 7, b: 2 }`, then `"a - b"` returns `5`,
  `"a * b"` returns `14`, `"a / b"` returns `3.5`, `"a % b"` returns `1`, and `"-a"` returns `-7`.
- **AC-4**: Given `evaluateNumber("a - b - c", { a: 10, b: 3, c: 2 })`, then it returns `5`
  (left associativity), and given `evaluateNumber("a / b / c", { a: 12, b: 3, c: 2 })`, then it
  returns `2`.
- **AC-5**: Given `evaluateNumber` with whitelisted calls, then `"abs(0 - 5)"` returns `5`,
  `"min(a, b)"` with `{a:3,b:9}` returns `3`, `"max(a, b)"` with `{a:3,b:9}` returns `9`,
  `"floor(a / b)"` with `{a:7,b:2}` returns `3`, `"ceil(a / b)"` with `{a:7,b:2}` returns `4`,
  and `"gcd(a, b)"` with `{a:12,b:18}` returns `6`.
- **AC-6**: Given `evaluatePredicate("a + b <= 20", { a: 9, b: 9 })`, then it returns `true`;
  given `{ a: 15, b: 9 }`, then it returns `false`.
- **AC-7**: Given `evaluatePredicate` with `{ a: 5, b: 5 }`, then `"a == b"` is `true`,
  `"a != b"` is `false`, `"a < b"` is `false`, `"a <= b"` is `true`, `"a > b"` is `false`, and
  `"a >= b"` is `true`.
- **AC-8**: Given `evaluatePredicate("a > 0 && b > 0 || a == 0", { a: 0, b: 0 })`, then it
  returns `true` (`&&` binds tighter than `||`).
- **AC-9**: Given `evaluateNumber("a + z", { a: 1 })` where `z` is not in the environment, then
  it throws an `ExprError` whose `code` is `UNKNOWN_IDENTIFIER` and whose message names `z`.
- **AC-10**: Given `evaluateNumber("foo(a)", { a: 1 })`, then it throws an `ExprError` with
  `code` `UNKNOWN_FUNCTION`; given `evaluateNumber("min(a)", { a: 1 })`, then it throws an
  `ExprError` with `code` `ARITY_MISMATCH`.
- **AC-11**: Given a malformed input — each of `"a +"`, `"(a + b"`, `"a ** b"`, `""`, `"a b"`,
  `"a $ b"` — then `evaluateNumber` throws an `ExprError` with `code` `PARSE_ERROR`.
- **AC-12**: Given `evaluateNumber("a / b", { a: 1, b: 0 })` or `"a % b"` with `b = 0`, then it
  throws an `ExprError` with `code` `DIVISION_BY_ZERO` — it never returns `Infinity` or `NaN`.
- **AC-13**: Given `evaluateNumber("a > b", { a: 2, b: 1 })`, then it throws an `ExprError` with
  `code` `TYPE_MISMATCH`; given `evaluatePredicate("a + b", { a: 1, b: 1 })`, then it throws an
  `ExprError` with `code` `TYPE_MISMATCH`.
- **AC-14**: Given the same expression string and the same environment, when evaluated 100
  times, then every result is identical — evaluation is pure and holds no cross-call state.
- **AC-15**: Given an expression nested more deeply than the parser's depth limit (e.g. 200
  nested parentheses), then it throws an `ExprError` with `code` `PARSE_ERROR` rather than
  overflowing the stack.
- **AC-16**: Given `"a % b"` with a **negative left operand** (`{a:-7,b:2}`), then it returns
  `-1` — JavaScript remainder semantics, where the sign follows the dividend — not `1`
  (mathematical modulo). Given `{a:7,b:-2}` it returns `1`.
  *(Orchestrator 2026-07-27. Was unspecified and matters directly: T-016 asserts divisibility
  via `"a % b == 0"`, and that idiom is correct under either convention, so the cheaper and
  less surprising choice is the language's own. A template needing true modulo writes
  `((a % b) + b) % b`.)*
- **AC-17**: Given `"gcd(a, b)"`, then it operates on absolute values — `{a:-12,b:18}` returns
  `6`, `{a:12,b:-18}` returns `6` — and `{a:0,b:5}` returns `5`, `{a:0,b:0}` returns `0`.
  *(Orchestrator 2026-07-27. Was unspecified; zero and negative arguments are reachable from
  constraint expressions and would otherwise be implementation-defined or hang.)*
- **AC-18**: Given a whitelisted function called with **zero arguments** (`"abs()"`), then it
  throws `PARSE_ERROR`, not `ARITY_MISMATCH`.
  *(Orchestrator 2026-07-27, resolving a genuine contradiction the Test Agent surfaced rather
  than guessed at: the grammar's `args := expr ( "," expr )*` requires at least one argument,
  so a zero-argument call never reaches the arity check. The grammar is declared complete and
  authoritative, so it wins. `ARITY_MISMATCH` remains correct for one-too-few or one-too-many.)*
- **AC-19**: Given the module's exports, then `ExprErrorCode` is a **type-only** export — a
  union of the string-literal codes — and `ExprError` is a runtime class extending `Error`
  carrying a `code: ExprErrorCode`. Importing `ExprErrorCode` as a value is a compile error.
  *(Orchestrator 2026-07-27. The DoD required exporting it without saying whether it was a type
  or a runtime value; the two are not interchangeable at the import site, so consumers in
  T-005/T-007 would have had to guess.)*
- **AC-20**: Given an expression nested **16 levels** deep, then it evaluates successfully.
  *(Orchestrator 2026-07-27, adopting the Test Agent's inference as an explicit criterion. AC-15
  alone is satisfied by a depth limit of 2, which would reject legitimate templates while
  passing the suite — the L-006 failure mode. This pins a usable floor without dictating the
  exact limit.)*
