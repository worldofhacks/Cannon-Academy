## Context

One interface, three eventual implementations: the scripted onboarding sloop (here), the banded
mercy bot (T-021), and — someday — a ghost captain replaying a recorded action log
(ARCHITECTURE.md §13, not built). The reducer never knows which it is facing.

```ts
export interface Opponent {
  readonly id: string;
  chooseAction(view: RivalView): Promise<RivalAction>;                     // { cannonId }
  produceAnswer(question: Question): Promise<OpponentAnswer>;              // { correct, elapsedMs }
}
export interface OpponentAnswer { readonly correct: boolean; readonly elapsedMs: number }

export interface ScriptedStep {
  readonly cannonId: CannonId; readonly correct: boolean; readonly elapsedMs: number;
}
export function createScriptedOpponent(input: {
  readonly id: string;
  readonly script: readonly ScriptedStep[];   // >= 1 step
}): Opponent;
```

**The scripted opponent** walks its script one step per turn. Calls alternate
`chooseAction` → `produceAnswer` for a given step; `chooseAction` advances the cursor and
`produceAnswer` reports that same step's `correct`/`elapsedMs`. Once the script is exhausted it
**repeats its final step forever** rather than throwing — an onboarding duel that runs one volley
longer than expected must not crash a five-year-old's first ninety seconds.

**The onboarding sloop** PLAN.md describes ("politely sinks in three volleys") is expressed as a
script of three low-damage, mostly-incorrect steps plus the enemy hull tuning that lets three
player volleys finish it. This ticket ships the *mechanism* and a fixture proving the shape; the
concrete onboarding script is assembled by the caller from `ScriptedStep`s.

## Planning Decisions

- `locked-decision` — the two-method, Promise-returning interface exactly as ARCHITECTURE.md §4.2
  writes it. The engine is otherwise synchronous; this is the one deliberate async seam, and it
  exists so a network player can fill it unchanged.
- `locked-decision` — **no wall-clock anywhere.** `elapsedMs` is scripted or PRNG-drawn, never
  measured; `Date` is lint-banned in `src/engine/**`. Any "thinking delay" a player perceives is
  the store driver's `setTimeout`, which is presentation-only and out of this swarm's scope.
- `proposed` — Promises resolve immediately (a resolved promise, no timer). An engine that
  schedules real time would be untestable and non-replayable. AC-8 pins this by asserting the
  full script completes within a single test tick with fake timers unused.
- `proposed` — script exhaustion repeats the last step. The alternatives were throwing (crashes
  onboarding) or ending the duel (the reducer, not the opponent, decides that).
- `proposed` — `Opponent` carries an `id` so the action log and any future `duels/{id}` document
  can name the rival without the reducer knowing its type.
- `proposed` — `createScriptedOpponent` is a factory returning a fresh object with private cursor
  state. This is the one place in `src/engine/**` that holds mutable state across calls, and it is
  unavoidable: the interface is stateful by ARCHITECTURE.md's design. It is not part of
  `DuelState` and is never serialised, so replay reconstructs it from the action log instead
  (T-023).

## Acceptance Criteria

- **AC-1**: Given `createScriptedOpponent` with a 3-step script, when the returned object is
  inspected, then it satisfies the `Opponent` interface (`id` string, `chooseAction` and
  `produceAnswer` both functions) and its `id` equals the supplied id.
- **AC-2**: Given a 3-step script, when `chooseAction` then `produceAnswer` are awaited three
  times in sequence, then the three `(cannonId, correct, elapsedMs)` triples equal the three
  script steps in order.
- **AC-3**: Given a 3-step script, when the pair is awaited a fourth and fifth time, then both
  return the third step's values — the script repeats its final step rather than throwing or
  returning `undefined`.
- **AC-4**: Given a script whose steps have `correct: false`, when `produceAnswer` is awaited,
  then `correct` is `false` and `elapsedMs` is the scripted value — the opponent never inspects
  the question's `correctIndex` or `choices` to decide.
- **AC-5**: Given `createScriptedOpponent` with an empty script, when called, then it throws a
  `RangeError`.
- **AC-6**: Given a script step with a negative `elapsedMs`, or a `cannonId` absent from the
  catalog, when the opponent is created, then it throws an `Error` naming the offending step
  index.
- **AC-7**: Given two opponents created from the same script, when both are driven through five
  turns, then their emitted triples are element-wise identical — construction carries no
  hidden nondeterminism.
- **AC-8**: Given a 3-step script, when all three turns are awaited inside a single test without
  advancing any timer, then all promises resolve — the opponent schedules no real time and
  depends on no clock.
- **AC-9**: Given the module sources under `src/engine/opponents/`, when their text is scanned,
  then they contain none of `Date`, `Math.random`, `setTimeout`, `setInterval`, or
  `performance.now`.
- **AC-10**: Given `produceAnswer` called with any `Question`, when the returned `elapsedMs` is
  inspected, then it is a finite non-negative number, and the returned object has exactly the
  keys `correct` and `elapsedMs`.
- **AC-11**: Given `chooseAction` called with a `RivalView`, when the returned `RivalAction` is
  inspected, then it has exactly the key `cannonId`, and the value appears in the view's
  `rivalLoadout` whenever the script's cannon is in that loadout.
- **AC-12**: Given a scripted opponent driven through a script whose steps are all
  `correct: false`, when the sequence of results is inspected, then no step's outcome depends on
  the `RivalView` passed in — passing two different views yields identical results.
