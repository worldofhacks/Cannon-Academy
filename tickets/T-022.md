## Context

The third leg of PLAN.md's "difficulty is a strategic choice" argument, after gun selection and
temperaments. This ticket extends the base machine T-020 shipped; it is the **sole owner of
`duel/types.ts` and `duel/reducer.ts` in wave 6**, so T-013's and T-020's frozen tests must
continue to pass unmodified. Two things were put in place upstream specifically so this ticket
patches rather than supersedes: T-013 AC-11 states `ActionLogEntry`'s closed set over *required*
fields only, and both T-013 and T-020 require their tests to enumerate phases and events as
hardcoded literal arrays rather than deriving them from the exported unions.

**Design.** `playerChoose` gains a second way out. Instead of `CANNON_SELECTED`, the player may
dispatch `DOUBLE_SHOT_SELECTED { cannonId }`, which enters `reload` on the same cannon and the
same skill but with

```
timerMs = round(cannon.timerMs * DOUBLE_SHOT_TIMER_FACTOR)     // < cannon.timerMs
doubleShot = true
```

On a **correct** answer, `resolveShot` is run `DOUBLE_SHOT_VOLLEY_COUNT` (≥2) times against the
same cannon and answer quality, drawing from the PRNG once per volley, and the outcomes are
summed into a single `ShotOutcome` whose `ballCount` and `damageToEnemy` are the totals. On a
**wrong answer or timeout**, the turn resolves exactly as a normal misfire does — including
volatile recoil, applied once.

Because `answerQuality = 1 - elapsedMs / timerMs`, a shortened timer makes the same question
strictly harder: lower quality for the same thinking time, and a proportionally smaller Perfect
Shot window. No new difficulty taxonomy is introduced.

**Type changes (all additive):**

- `DuelEvent` gains `{ type: 'DOUBLE_SHOT_SELECTED'; cannonId: CannonId }`.
- The `reload` and `resolvePlayer` phases gain `readonly doubleShot: boolean`.
- `ActionLogEntry` gains `readonly doubleShot?: boolean`, so T-024 AC-19 can replay the turn.

## Planning Decisions

- `locked-decision` — **"A harder variant of the same skill" means the same question pool under a
  shortened timer.** *Owner ruling D-2, 2026-07-27.* PLAN.md did not define it and no difficulty
  taxonomy existed. The two candidate readings were (a) draw from harder templates — needing a
  schema change plus a difficulty rating for ~72 authored templates — and (b) the same question
  under more pressure. The owner ruled (b). It composes with the existing quality curve, needs no
  content change, and shrinks the Perfect Shot window proportionally. **Closed.**
  `templateSchema`'s `difficulty?: 1 | 2 | 3` (T-003 AC-17) stays as declared insurance and
  remains **unread** by T-007 and by every content ticket.
- `proposed` — a wrong Double-Shot answer is punished no more than a normal miss (same recoil,
  once). PLAN.md describes the opt-in as a risk/reward choice but attaches no extra penalty; the
  risk is the shortened timer and the forfeited safe volley.
- `proposed` — the extra volleys draw independently from the PRNG rather than doubling one roll,
  so a Double-Shot reads as genuine extra shot spread and its variance is honest.
- `proposed` — `ActionLogEntry` gains one optional field. This deviates from ARCHITECTURE.md
  §4.2's four-field log, and it is necessary: without it a Double-Shot turn cannot be replayed,
  which would silently break the §13 ghost-captain path. Optional, so existing logs stay valid.
- `locked-decision` — no new *phase*. Double-Shot is a modifier on `reload`/`resolvePlayer`, so
  ARCHITECTURE.md §4.2's eight-phase list is unchanged and T-024's fuzz coverage still applies.

## Acceptance Criteria

- **AC-1**: Given the base machine's frozen tests from T-013 and T-020, when the full suite is
  run after this ticket's changes, then every one of them passes **unmodified** — no existing
  test file is edited by this ticket.
- **AC-2**: Given a `playerChoose` state, when `DOUBLE_SHOT_SELECTED` names a cannon in
  `playerLoadout`, then the phase is `reload`, `doubleShot` is `true`, `cannonId` matches, and
  `timerMs === Math.round(cannon.timerMs * DOUBLE_SHOT_TIMER_FACTOR)`, which is strictly less
  than `cannon.timerMs`.
- **AC-3**: Given a `playerChoose` state, when `CANNON_SELECTED` is dispatched, then `doubleShot`
  is `false` and `timerMs === cannon.timerMs` — the default path is unchanged.
- **AC-4**: Given a `playerChoose` state, when `DOUBLE_SHOT_SELECTED` names a cannon not in
  `playerLoadout`, then the returned state is the identical object reference.
- **AC-5**: Given a `reload` state with `doubleShot: true`, when a correct answer is given, then
  `outcome.damageToEnemy` equals the sum of `DOUBLE_SHOT_VOLLEY_COUNT` independent rolls,
  `outcome.ballCount` equals the sum of the per-volley ball counts, and `enemyHull` decreased by
  that total.
- **AC-6**: Given identical `(cannon, elapsedMs, rng)`, when a Double-Shot correct answer and a
  normal correct answer are each resolved, then the Double-Shot `damageToEnemy` is strictly
  greater than the normal one.
- **AC-7**: Given a `reload` state with `doubleShot: true` on a volatile cannon, when a wrong
  answer is given, then `playerHull` decreased by exactly `cannon.recoilDamage` (once, not
  `DOUBLE_SHOT_VOLLEY_COUNT` times), `enemyHull` is unchanged, and `outcome.kind` is `"misfire"`.
- **AC-8**: Given a `reload` state with `doubleShot: true`, when `TIMER_EXPIRED` is dispatched,
  then it resolves as a miss with `elapsedMs` equal to the **shortened** `timerMs`, not the
  cannon's full timer.
- **AC-9**: Given a Double-Shot on a cannon with `timerMs === 20000` and
  `shortened = Math.round(20000 * DOUBLE_SHOT_TIMER_FACTOR)`, when resolved at
  `elapsedMs = Math.ceil(0.4 * shortened) - 1`, then `outcome.perfectShot` is `true`; at
  `elapsedMs = Math.ceil(0.4 * shortened)` it is `false`; and at any `elapsedMs` in
  `[0.4 * shortened, 0.4 * 20000)` — a window that *would* be a Perfect Shot under the full
  timer — it is `false`. The boundary is strict `<` against the **shortened** timer, tested with
  the same exact off-by-one rigour as T-008 AC-3, including the rounding direction of
  `Math.round(cannon.timerMs * DOUBLE_SHOT_TIMER_FACTOR)`.
- **AC-10**: Given a Double-Shot turn, when the appended `ActionLogEntry` is inspected, then it
  has `doubleShot: true` alongside the four base fields; and given a normal turn, then
  `doubleShot` is absent or `false`.
- **AC-11**: Given a `reload`, `resolvePlayer`, `rivalTurn`, `resolveRival`, `victory`, or
  `defeat` state, when `DOUBLE_SHOT_SELECTED` is dispatched, then the returned state is the
  identical object reference in every case — the new event obeys the same out-of-phase no-op rule.
- **AC-12**: Given a Double-Shot correct answer, when the tally is inspected, then
  `tally.totalAnswers` and `tally.correctAnswers` each increased by exactly `1`, and
  `tally.bySkill` for that skill gained exactly one attempt — one question answered is one
  answer, regardless of how many volleys it fired.
- **AC-13**: Given the same config and the same event sequence including Double-Shot turns, when
  the duel is run 20 times, then all 20 final states are deeply equal; and every intermediate
  state still survives a JSON round-trip.
- **AC-14**: Given a Double-Shot volley that brings `enemyHull` below `0`, when `ANIMATION_DONE`
  is dispatched, then the phase is `victory` and `enemyHull` is exactly `0`.
