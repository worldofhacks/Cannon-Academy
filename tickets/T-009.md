## Context

Two pure functions: what a duel pays, and what a chest turns out to be.

```ts
export interface DuelPerformance {
  readonly won: boolean;
  readonly correctAnswers: number;   // integer >= 0
  readonly totalAnswers: number;     // integer >= correctAnswers
  readonly perfectShots: number;     // integer >= 0, <= correctAnswers
}
export function computeCoinPayout(p: DuelPerformance): number;   // integer > 0

export interface ChestDrop { readonly rarity: ChestRarity; readonly coins: number }
export function rollChest(rng: Rng): readonly [ChestDrop, Rng];
```

**Payout shape** (coefficients all from `tuning.ts`, T-004):

```
base     = p.won ? COINS_WIN_BASE : COINS_LOSS_BASE
accuracy = p.totalAnswers === 0 ? 0 : p.correctAnswers / p.totalAnswers
payout   = round(base
                 + COINS_PER_ACCURACY_PERCENT * (accuracy * 100)
                 + COINS_PER_PERFECT_SHOT * p.perfectShots)
```

**Chest roll:** two draws from the same stream, in this order — rarity, then coins.

`CHEST_RARITY_WEIGHTS` is a `Record<ChestRarity, number>` (T-004) but T-001's `weightedPick`
takes an **array** of `{ item, weight }` entries, so a conversion is required and its ordering
feeds the PRNG. **Pin it:** this module exports

```ts
export const CHEST_RARITY_ENTRIES: readonly { item: ChestRarity; weight: number }[];
```

built by mapping the `ChestRarity` id array exported by T-003 — **not** `Object.entries` over the
record — so the order is exactly `common, uncommon, rare` and cannot drift with a key
reordering in `tuning.ts`. Then `weightedPick(rng, CHEST_RARITY_ENTRIES)` for the rarity and
`nextInt(rng, r.min, r.max)` from `CHEST_COIN_RANGE_BY_RARITY[rarity]` for the coins.

## Planning Decisions

- `open-question` — **the payout coefficients themselves.** PLAN.md specifies the payout's
  *inputs* ("win, accuracy, perfects") and two qualitative facts ("a small purse" on a loss;
  losing still pays) and no numbers at all. The shape above is `proposed`; every coefficient is
  a named T-004 constant, and AC-2 … AC-6 pin the behaviour that matters — a loss pays less than
  a win, a loss still pays something, and payout rises with accuracy and with perfects. Listed
  for the human in `.tdd-swarm/traceability.md`.
- `proposed` — linear in accuracy and in perfect count. The simplest shape that satisfies
  PLAN.md's three named inputs; anything richer would be invented design.
- `scope-cut` — **a chest yields a rarity and a coin amount, nothing else.** PLAN.md lists
  cannons, crew, and cosmetics as possible chest contents, but the same document's day-2 line is
  "treasure chest as a plain rarity roll" and the first cut is "treasure-chest ceremony → plain
  coin payout". Item resolution also needs a cosmetics catalog that does not exist and player
  unlock state that is store-owned. Recorded as a planning gap in
  `.tdd-swarm/traceability.md`, not silently dropped.
- `proposed` — payouts round to an integer. Coins are a counted currency; fractional coins would
  leak into the persisted profile (ARCHITECTURE.md §5).

## Acceptance Criteria

- **AC-1**: Given any valid `DuelPerformance`, when `computeCoinPayout` is called, then the
  result is a finite integer strictly greater than `0` — every duel pays, including a loss with
  zero correct answers (PLAN.md: "last place still pays").
- **AC-2**: Given two identical performances differing only in `won`, when both are priced, then
  the winning payout is strictly greater than the losing payout.
- **AC-3**: Given performances with `totalAnswers = 10` and `correctAnswers` sweeping `0..10`,
  all else equal, when each is priced, then the payout sequence is non-decreasing, and the
  payout at `correctAnswers = 10` is strictly greater than at `correctAnswers = 0`.
- **AC-4**: Given performances with `perfectShots` sweeping `0..8`, all else equal, when each is
  priced, then the payout sequence is strictly increasing.
- **AC-5**: Given `totalAnswers === 0` (a duel abandoned before any answer), when priced, then
  the result is a finite integer `> 0` — never `NaN`.
- **AC-6**: Given a `DuelPerformance` with a negative field, a non-integer field,
  `correctAnswers > totalAnswers`, or `perfectShots > correctAnswers`, when priced, then it
  throws a `RangeError`.
- **AC-7**: Given the same `DuelPerformance`, when priced 100 times, then all 100 results are
  identical — the function consumes no randomness and holds no state.
- **AC-8**: Given `rollChest` called 100,000 times from `createRng(31337)` (threading the
  returned `Rng`), when the rarity counts are measured, then each rarity's observed frequency is
  within `0.01` absolute of its `CHEST_RARITY_WEIGHTS` value, and no rarity outside
  `ChestRarity` is ever produced.
- **AC-9**: Given any `rollChest` result, when inspected, then `coins` is an integer within
  `[CHEST_COIN_RANGE_BY_RARITY[rarity].min, CHEST_COIN_RANGE_BY_RARITY[rarity].max]` inclusive.
- **AC-10**: Given 100,000 seeded rolls, when grouped by rarity, then the mean `coins` of the
  `rare` group is strictly greater than that of the `uncommon` group, which is strictly greater
  than that of the `common` group — rarer chests pay better.
- **AC-11**: Given the same starting `Rng`, when `rollChest` is called, then it returns an
  identical `ChestDrop` and an identical advanced `Rng` on every repetition; and the returned
  `Rng` differs from the input.
- **AC-12**: Given `computeCoinPayout` and `rollChest` results, when a total is accumulated over
  1,000 seeded duels, then the running coin total is monotonically non-decreasing and never
  negative (ARCHITECTURE.md §9.2 invariant: never negative coins).
- **AC-13**: Given `CHEST_RARITY_ENTRIES`, when inspected, then it has exactly one entry per
  `ChestRarity`, its `item` values appear in the order `common, uncommon, rare`, and each
  `weight` equals `CHEST_RARITY_WEIGHTS[item]`. Given `CHEST_RARITY_WEIGHTS` rebuilt with its
  keys in a different insertion order, then `CHEST_RARITY_ENTRIES` is unchanged — the ordering
  that feeds the PRNG comes from T-003's id array, not from record key order.

## Test Plan

- Unit (deterministic): AC-1 … AC-7 — payout bounds, ordering, monotonicity in accuracy and in
  perfects, the zero-answer edge, argument validation, and purity.
- Unit (deterministic): AC-8, AC-9, AC-10 — fixed-seed rarity distribution against the declared
  weights, coin bounds per rarity, and the rarity→value ordering.
- Unit (deterministic): AC-11, AC-12 — determinism and the non-negative-coins invariant.
- Unit (deterministic): AC-13 — the record→entries conversion, whose ordering silently
  determines which rarity a given PRNG draw selects.
- Eval: none.
