## Reported

> "there is an error with the practice where the pirate seems to throw the object after the user
> shoots it and gets the answer right … if its right the user shoots it, it explodes, and moves on
> to the next question."

## What is actually true

The toss-before-every-question beat is **designed** (board 11a: the target lands before the
question, `src/services/rangeRound.ts:9-19`) and frozen by `spec(A-059:AC-9)`
(`__tests__/app/range-round.test.ts:132-152`). That beat stays. The bug is real and it is a state
conflation, not the beat:

- `answerRound` stores the post-shot target as `afterShot(round.target, correct) ?? round.target`
  (`rangeRound.ts:195`). `afterShot` returns `null` both for *cleared* and for *missed*
  (`rangeTargets.ts:140-144`), and the `??` resurrects the dead object so the verdict has
  something to shatter. The "destroyed" fact is erased from state.
- `advanceRound` then re-derives what is standing from the resurrected value
  (`rangeRound.ts:221`): a crate whose final crate was just smashed is stuck at
  `{kind:'crate', remaining:1}`, passes the check, and `nextTarget` short-circuits on a standing
  target (`rangeTargets.ts:93-96`) — **the same crate is the target for the rest of the round.**
  After every later correct answer the child watches it explode into shards and then Pim visibly
  re-throws the identical object with the `PIM TOSSES` chip. The coalesce also lets a crate stack
  survive a MISS, contradicting the module's own contract "never survives a miss"
  (`rangeTargets.ts:133-138`).
- Separately, the toss animation and chip key on the bare condition `phase === 'incoming'`
  (`app/range.tsx:1033-1037`, `:673-675`), so even the *designed* one-crate carry (first hit of
  two) is animated as a fresh throw of an object that is already in the water.

## Fix

Represent survival honestly instead of guessing it back:

- `RangeRound` gains `readonly survivor: StandingTarget | null` (`openRound` sets `null`).
  `answerRound` keeps `target: round.target` for the verdict display and sets
  `survivor: afterShot(round.target, correct)` — raw, `null` allowed.
- `advanceRound` replaces the line-221 derivation with `round.survivor`. `afterShot`'s semantics
  (null on miss, null on final crate, `{crate,1}` on first hit) are exactly the standing
  semantics wanted.
- The advanced round exposes `carried: boolean` (survivor was non-null). The screen skips the
  toss animation and prints a continuation chip (e.g. `ONE CRATE LEFT!`) instead of `PIM TOSSES`
  when `carried` is true.

`RangeRound` is component state, never persisted — no captain field, no schema concern.

## Acceptance criteria

- **AC-1**: After a correct answer clears the **last** crate of a stack, the following target is a
  fresh draw — never the destroyed crate. Proven by playing a real round (seed-hunted to reach a
  crate) through hit→hit and asserting the target changes after the stack dies.
- **AC-2**: A crate stack never survives a miss: after a wrong answer on a crate, the following
  target is a fresh draw — the module contract "never survives a miss" holds at round level.
- **AC-3**: The designed one-crate carry is preserved: the first hit on a two-crate stack leaves
  `{crate, remaining: 1}` standing and `nextTarget`'s no-re-roll short-circuit still holds
  (frozen `spec(A-059:AC-11)` behaviour unchanged).
- **AC-4**: The screen never replays the toss for a carried target: `carried` is exposed on the
  round, the toss animation and `PIM TOSSES` chip fire only for genuinely new targets, and a
  carried target gets continuation copy instead.
- **AC-5**: Replay and the frozen surface are untouched: rounds remain a pure function of
  `{seed, answers}`, and every existing frozen `spec(A-059:*)` in `range-round.test.ts` passes
  without modification.

## Constraints

- The range has no timer by design (D-8); "timeout" is not a trigger on this screen.
