## Context

Authentication can be bootstrapped independently, but uploading the live `Captain` object would
freeze an accidental schema and publish a child-entered captain name that the MVP posture permits
only while local. Product tickets also add durable mercy and reward-receipt fields. One explicit
mapper and one subscription must own every cloud write after those contracts settle.

## Planning Decisions

- **[locked-decision]** AsyncStorage remains authoritative during play. This ticket is local-to-
  cloud sync only; a remote document never overwrites local progress.
- **[locked-decision]** `private-profile-v1` is a deterministic allow-listed projection. It omits
  captain name, device identifiers, raw reward receipts, and all other free text. The privacy
  posture therefore remains truthful without adding a wordlist.
- **[locked-decision]** One post-hydration captain-store subscription coalesces changes and writes
  the latest full projection. Duel settlement, range mastery, Harbor purchase, onboarding, and
  foreground retry use that one dispatcher rather than bespoke write calls.
- **[locked-decision]** Only `users/{uid}` is readable/writable by that UID. Rules validate the
  exact top-level keys, schema version, primitive/container types, and bounded arrays; every other
  path is denied.
- **[locked-decision]** Failed/offline writes remain queued in memory for the next state change or
  foreground retry and never block routing, local persistence, or gameplay.

## Acceptance Criteria

- **AC-1**: Given any `Captain`, when mapped to `private-profile-v1`, then the payload is
  deterministic, versioned, contains only the documented allow-list, deliberately converts
  mastery/mercy, and contains no name, device identifier, receipt payload, or free text.
- **AC-2**: Given hydration and an authenticated UID, when the captain changes through duel
  settlement, range mastery, Harbor purchase, or onboarding, then the same subscriber emits one
  coalesced full-profile write with merge semantics and the latest projection.
- **AC-3**: Given no UID, missing Firebase config, offline Firestore, or a rejected write, when
  local state changes, then no unhandled rejection or local rollback occurs and the latest
  projection retries on foreground.
- **AC-4**: Given an app launch, when local hydration is incomplete, then no Auth/Firestore work
  extends the splash gate; after hydration, identity and sync start exactly once and clean up on
  unmount.
- **AC-5**: Given Firestore emulator rule tests, then an anonymous user can create/read/update only
  their own shape-valid `users/{uid}` document; cross-user, extra-field, wrong-type, wrong-version,
  delete, and every non-user path request are denied.
- **AC-6**: Given the configured Firebase project, when release evidence runs, then one online
  owner-only profile write/read succeeds against the `nam5` default database and the deployed
  rules version/commit is recorded.

## Test Plan

- Unit (deterministic): exact mapper, subscription/coalescing, all named mutation boundaries,
  foreground retry, cleanup, unauthenticated/offline behavior, and no remote-to-local path.
- Rules integration: `@firebase/rules-unit-testing` against the Firestore emulator for every allow
  and deny case; deployed online smoke is release evidence, not a mocked unit test.

## Definition of Done

- [ ] Tests are RED, independently reviewed, and frozen before implementation.
- [ ] Any required rules-test package is dev-only and security-reviewed.
- [ ] Captain name remains local-only and the privacy posture is updated.
- [ ] Rules are deployed to `cannon-academy` and their rollback commit is recorded.
- [ ] Local gates, emulator suite, code review, and Security Agent review pass.

## Out of Scope

Remote-to-local restore, multi-device conflict resolution, public leaderboard, account linking,
analytics, Storage uploads, and publishing captain names.
