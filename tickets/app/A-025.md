## Context

`firebase@12.16.0` and `@react-native-async-storage/async-storage@2.2.0` are already installed and
locked, but no production module imports them. The Firebase project `cannon-academy` exists and has
no registered app, Firestore database, environment contract, or rules files.

## Planning Decisions

- **[locked-decision]** Expo `EXPO_PUBLIC_*` values are Firebase client identifiers embedded in the
  bundle, not secrets. Service-account keys, Admin credentials, and privileged tokens are forbidden.
- **[locked-decision]** Missing or invalid config disables the backend and leaves local play
  available; it may not crash routing.
- **[locked-decision]** Native Auth is initialized with AsyncStorage persistence. Web uses browser
  Auth persistence. Firestore is configured for automatic long-polling detection before first use.
- **[locked-decision]** Storage is exported with deny-all rules. After the owner links Blaze
  billing, provision `cannon-academy.firebasestorage.app` in `us-central1`; gameplay does not wait
  on that bucket.
- **[locked-decision]** The Firebase Web app is the Expo JavaScript client for web and native.
  Its six public identifiers are written to ignored `.env.local` and EAS `production`/`preview`
  plaintext variables; no service credential is created or exposed.
- **[locked-decision]** Initial Firestore and Storage rules are deny-all. Safe infrastructure
  rollback removes the EAS values (forcing local-only mode) and redeploys the audited deny-all
  rules; permanent database/bucket resources are not destructively deleted.

## Acceptance Criteria

- **AC-1**: Given all six required `EXPO_PUBLIC_FIREBASE_*` values, when configuration is parsed,
  then a typed client config is returned; given any missing value, the result is explicitly
  disabled without logging values or throwing during module import.
- **AC-2**: Given iOS or Android, when the client initializes, then it creates one Firebase app and
  initializes Auth with `getReactNativePersistence(AsyncStorage)`; given web, it uses browser Auth
  and never supplies React Native persistence.
- **AC-3**: Given repeated module/bootstrap evaluation, when Firebase clients are requested, then
  one app, one Auth configuration, and one Firestore configuration are reused; only an
  already-initialized condition may fall back to the corresponding getter.
- **AC-4**: Given Firestore initialization, then
  `experimentalAutoDetectLongPolling: true` is applied before any Firestore getter, and `db` and
  `storage` are exported beside `auth`.
- **AC-5**: Given repository configuration, then `.env` variants are ignored, `.env.example`
  contains blank entries for exactly the six public keys, `.firebaserc` selects
  `cannon-academy`, and Firestore/Storage rules deny all access at this boundary.
- **AC-6**: Given the owner-approved Firebase project, when infrastructure is provisioned, then it
  has one registered Expo Web app, the `(default)` Firestore database in permanent location
  `nam5`, the exact default bucket `cannon-academy.firebasestorage.app` in `us-central1`, anonymous
  Auth enabled as the only sign-in provider, and deployed deny-all Firestore/Storage rules. This
  is process evidence; a deterministic test may freeze its evidence schema but cannot close it.
- **AC-7**: Given the retrieved Web SDK config, when local and EAS environments are inspected,
  then all six names exist with values matching that app in `.env.local`, EAS `production`, and
  EAS `preview`; repository history/logs contain no values beyond Firebase's public client
  identifiers and a config-free launch remains local-only. Live/local/EAS inspection is process
  evidence; unit tests cover only the parser and repository contract.
- **AC-8**: Given a failed or partial backend rollout, when the recorded rollback is executed,
  then clients can be returned to local-only mode and both data services to deny-all without
  deleting local Captain progress or changing the production Hosting alias. The rollback rehearsal
  is process evidence; unit tests cover only the fail-closed code/config boundary.

## Test Plan

- Unit (deterministic): injected SDK facade for AC-1 through AC-4, including call order and repeat
  initialization.
- Configuration guards (deterministic): file assertions for AC-5.
- Process evidence: run the idempotent package install command and prove the lockfile has no
  unintended dependency drift; record project/app IDs, database/bucket locations, provider state,
  rules release versions, EAS variable names, and a dry-run of the non-destructive rollback.
