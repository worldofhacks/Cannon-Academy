## Context

The current Captain has no mercy state or durable settlement ledger. A-008's `WeakMap` prevents
duplicate reward observation only until relaunch, and parallel opponent/profile/reward tickets
would otherwise invent incompatible persisted fields.

## Planning Decisions

- **[locked-decision]** Captain adds `mercyState`, `rewardReceipts`, and
  `nextPurchaseSequence` in one schema migration before any consumer ticket freezes.
- **[locked-decision]** A receipt key is exactly `duel:<duelId>` or
  `purchase:<non-negative sequence>`. Persisted receipt presence means the transaction committed;
  there is no separate mutable `applied` flag or timestamp.
- **[locked-decision]** `ChestReceipt` records source, deterministic seed, rarity, rolled coin
  fallback, and exactly one applied grant: coins or a cannon. A cannon receipt retains its unused
  coin fallback so a replay can prove it did not reroll.
- **[locked-decision]** The player module exposes a pure captain-tally transition so a later
  settlement can compute one next Captain snapshot and call `replaceCaptain` once.
- **[locked-decision]** Old saves migrate with empty mercy/receipts and sequence zero; corrupt
  receipt entries are dropped without discarding otherwise valid progress.

## Acceptance Criteria

- **AC-1**: Given a fresh Captain, when created, then mercy equals the engine empty state,
  `rewardReceipts` is empty, and `nextPurchaseSequence` is zero with fresh non-aliased containers.
- **AC-2**: Given a pre-ticket persisted Captain, when rehydrated, then every prior field is
  retained and the three new fields receive safe defaults; a second rehydrate is byte-equivalent.
- **AC-3**: Given shape-valid duel and purchase receipts, when persisted and relaunched, then their
  discriminants, keys, seeds, rarity, fallback, and applied grants round-trip exactly.
- **AC-4**: Given malformed receipt keys, negative sequences, duplicate keys, invalid cannon IDs,
  or impossible grants, when migrated, then those entries are rejected without granting coins or
  inventory.
- **AC-5**: Given a tally transition, when applied to a Captain snapshot, then it produces the
  same mastery/unlocks as the existing store action without mutating the input, allowing a later
  reward transaction to commit with one `replaceCaptain`.
- **AC-6**: Given mercy and receipt fields, when a Captain is replaced or persisted, then they are
  retained exactly and are available to the opponent and settlement services without a second
  schema.

## Test Plan

- Unit/property (deterministic): old/current/corrupt migration fixtures, receipt-key grammar,
  receipt round trips, non-aliasing, and pure tally parity with existing actions.
