## Context

The Gun deck already renders `captain.ownedCannons` correctly. The launch defect is one screen
earlier: `app/duel.tsx` discards `applyDuelOutcome`'s returned unlock delta, while `VictoryPanel`
always prints “Chain Shot / NEW CANNON” after every chest opens. A normal first win cannot unlock
Chain Shot, so the victory screen claims a grant the store never made. The fix is a truthful
presentation seam over the real outcome, not a second award rule.

## Acceptance Criteria

- **AC-1**: Given a victorious duel whose `DuelRewardOutcome.unlockedCannons` is empty, when the
  chest opens, then it shows the real coin payout and no cannon name or “NEW CANNON” claim.
- **AC-2**: Given a victorious duel whose outcome contains one or more newly unlocked cannon ids,
  when the chest opens, then every cannon shown is derived from those exact ids and no hardcoded
  cannon name can appear.
- **AC-3**: Given `applyDuelOutcome` settles a victory, when the screen observes the outcome, then
  the same outcome drives the panel and the captain store; an actually shown cannon is present in
  `ownedCannons` and therefore appears in the Gun deck hold as new.
- **AC-4**: Given the victory state is observed again after opening the chest or under a repeated
  effect, when the already-settled no-payment result occurs, then it cannot erase or replace the
  first applied reward presentation.

## Test Plan

- Unit (deterministic): a pure `victoryRewards(outcome)` projection for AC-1 and AC-2.
- Integration (deterministic): real `applyDuelOutcome` → projection → existing Gun-deck
  `deckSlots` for AC-3.
- Source contract (deterministic): the victory panel contains no authored cannon name and the
  screen retains the first applied outcome for AC-2/AC-4.
- Native smoke (release evidence): win, open chest, then open Gun deck and reconcile every shown
  cannon with the deck.
