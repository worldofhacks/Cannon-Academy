## Context

The repository has two duel reducers. `src/engine/duel/reducer.ts` owns replay, action logs, rival
volleys, and turn tokens, while `src/stores/duel.ts` is the reducer the live screen actually uses
and still reimplements damage, RNG, tallies, hull, and payout. Their timeout rules already
disagree. Extending both would make every later duel ticket unsafe.

## Planning Decisions

- **[locked-decision]** `src/engine/duel/{types,reducer}.ts` becomes the sole gameplay state
  machine. The app store becomes a thin presentation-beat adapter and may not call `resolveShot`,
  `computeCoinPayout`, question generation, or mutate hull/tallies/RNG itself.
- **[locked-decision]** A timeout is a distinct logged result. It costs the turn but changes no
  answer tally, mastery projection, hull, recoil, or mercy accuracy. The engine retains the
  question long enough for the app's full teaching beat before advancing.
- **[locked-decision]** The core configuration carries explicit `duelId`, island, both loadouts,
  templates, and optional enemy-hull/player-hull-floor overrides. Defaults preserve a normal duel;
  the floor exists only for the guided mode.
- **[locked-decision]** Rival events carry the turn token they answer. A mismatched or stale token
  is a pure no-op before any damage or log entry.
- **[locked-decision]** Presentation beats may hold or subdivide a core phase for animation, but
  they project the core's values and never maintain a second authoritative copy.

## Acceptance Criteria

- **AC-1**: Given any normal duel action sequence, when it is driven through the app adapter, then
  hull, RNG, question, damage, tallies, action log, and terminal result come only from the engine
  state; the app reducer contains no independent gameplay calculation.
- **AC-2**: Given `TIMER_EXPIRED`, when the timeout teaching beat and following rival turn
  complete, then the timeout is replayable in the action log, the turn advances, and answer totals,
  per-skill attempts, mastery projection, hull, and mercy accuracy are unchanged.
- **AC-3**: Given correct, wrong, perfect, timeout, rival-hit, rival-miss, victory, and defeat core
  transitions, when projected, then the adapter emits the existing ordered presentation beats
  without dispatching the underlying engine event more than once.
- **AC-4**: Given a seed, configuration, and complete event log, when replayed, then the terminal
  state and presentation projection are identical, including timeout and rival events.
- **AC-5**: Given a rival result with an old turn token or a result arriving after reset/unmount,
  when submitted, then the exact current state reference is retained and no damage, log, reward,
  or UI update occurs.
- **AC-6**: Given each valid island and guided overrides, when the core is created, then tuned hull,
  explicit loadouts, `duelId`, and hull floor are retained; omitted overrides preserve current
  normal-duel behavior.
- **AC-7**: Given a terminal engine state, when the current reward projection reads it, then coins,
  win/loss, per-skill tallies, and rank inputs match the core result exactly and repeated
  observation remains idempotent pending A-032's durable receipt.

## Test Plan

- Engine unit/property (deterministic): D-8 timeout, event-log replay, token mismatch, defaults,
  guided floor, and every terminal path.
- Adapter unit/property (deterministic): every core-to-beat mapping, duplicate animation ticks,
  reset/unmount cancellation, and source guards against duplicated rule imports.
- Reward compatibility: existing A-008 behavior reads the canonical terminal projection.
