## Context

**Retrospective, like A-016.** Checklist item 10 is "time out a question and see the misfire". It is
implemented — `TIMEOUT` in `src/stores/duel.ts` moves to the `timeout` phase, increments `asked`,
tallies the skill, applies no recoil, and `PHASE_DURATION_MS.timeout` holds the panel for 2400 ms
carrying the correct answer — and no ticket has ever specified it.

It is separated from A-016 rather than folded into it for two reasons. It is a distinct concern: a
burned fuse is not a wrong answer, and the whole design point is that the two resolve differently.
And it carries an **open owner decision** (below) that A-016 does not, which needs to be visible on
its own rather than buried as one criterion in nine.

**Expected implementation delta: small and ruled.** The owner ruled on the question below on
2026-07-29 (D-8): a timeout counts against nothing. The delta is the exclusion in the `TIMEOUT`
case and nothing else — the copy already says "Nothing lost." and the ruling makes it true.

## Planning Decisions

### RULED — D-8, 2026-07-29: a timeout counts against nothing

**The owner chose resolution 2 below ("Exclude it"), in session, with the trade-offs in front of
them.** A timeout counts in neither `asked` nor `correct`, in both the aggregate counter and the
per-skill tally. The panel copy is unchanged and becomes true. The range lane's half of the same
ruling — `src/engine/drill.ts` counts an expired timer as an incorrect attempt — is engine-track
scope and is delegated to the engine agent under the same ruling; the tally rule must not drift
between the two lanes. The original open question is preserved below as written, because the
arguments are the record of why the ruling was needed.

### The question as it stood (`open — owner`, now ruled): does a timeout count against mastery accuracy?

**Today it does, and nobody decided that.** It emerged from two agents working independently, and
the two halves now disagree in front of a child:

- `src/stores/duel.ts` counts a timeout as `asked + 1` in both the aggregate counter and the
  per-skill tally, and never as `correct`. `src/services/duelRewards.ts` passes that tally
  straight into `recordDuelAnswers`, so the skill's `accuracy` falls.
- `src/engine/mastery.ts` gates every unlock on `weightedCorrect >= MASTERY_THRESHOLD_CORRECT`
  **and** `accuracy >= MASTERY_MIN_ACCURACY` (0.7). So a child who times out often enough can fill
  the meter and still be refused the cannon.
- `app/duel.tsx` tells them, in the timeout panel: **"Damp powder. The fuse burned out. Nothing
  lost."** — which is false about the only thing a mastery meter measures.

**The reducer's own comment argues the current behaviour is right**, and the argument is a good one:
"it counts as asked so accuracy stays honest… it counts as asked in the per-skill tally for the same
reason: the two must always sum to the same total, or the mastery meter and the scoreboard tell a
child two different stories."

The counter-argument is the audience. Kindergartners time out because they are five, not because
they are wrong, and a 20-second fuse plus a slow reader is a systematic accuracy penalty for reading
speed on a game whose stated pedagogy is that fluency shapes the quality of an action and never
permission to act.

**The three coherent resolutions**, all one-line changes, none of which this ticket takes:

1. **Keep it.** A timeout counts as `asked`. Then the panel copy is wrong and must change — "the
   fuse only decides how hard the shot lands" is not true when it also decides whether the cannon
   unlocks.
2. **Exclude it.** A timeout counts in neither `asked` nor `correct`, in both the aggregate and the
   per-skill tally. The copy becomes true and the meter simply advances more slowly.
3. **Split the counters.** Keep it in the duel scoreboard, exclude it from the mastery tally. This
   is the option the reducer's comment explicitly warns against, because the two totals then differ.

**This matters beyond the duel.** A-009's gunnery range credits mastery through the same
`{correct, asked}` tally shape via `recordRangeAnswers`, so whichever way this is ruled has to be
ruled once, in the tally, or the two lanes will drift apart. AC-5 below pins the decision _as it
stands_ so it is at least visible and regression-protected; a ruling changes AC-5 and the copy, and
nothing else.

## Acceptance Criteria

- **AC-1**: Given a question in flight, when the fuse expires, then the phase becomes `timeout`,
  `picked` is null, and **neither `asked` nor `right` changes** — a burned fuse is not an attempt
  (D-8). The turn is the whole cost, and AC-4 is where that cost is paid.
- **AC-2**: Given a timeout, when it resolves, then the player's hull is unchanged and the rival's
  hull is unchanged — the gun never fired, so there is no recoil and no damage. This is what
  distinguishes a burned fuse from a wrong answer, which can carry the engine's `damageToSelf`.
- **AC-3**: Given the `timeout` phase, when it is held, then it lasts `PHASE_DURATION_MS.timeout`
  and the panel it renders carries the expired question with its correct answer substituted in —
  the same teaching moment the `miss` phase gets, and the reason both holds are the longest in the
  machine.
- **AC-4**: Given a timeout that does not sink the player, when the hold ends, then the turn passes
  to the rival exactly once and the duel continues; given `TIMEOUT` dispatched from any phase other
  than `question`, or with no cannon picked, then the state is returned unchanged.
- **AC-5**: Given a timed-out question, when the per-skill tally is inspected, then that skill's
  entry is unchanged in **both** fields — accuracy neither falls nor rises, and a timeout can
  never delay a cannon unlock (D-8). The panel's "Nothing lost." is now a fact about the mastery
  meter, and `resolveCopy`'s timeout branch must keep saying it.
- **AC-6**: Given any action log containing timeouts, when the state is inspected, then the
  per-skill `asked` values still sum to the aggregate `asked` — whatever the owner rules, the
  scoreboard and the mastery meter count the same events.
