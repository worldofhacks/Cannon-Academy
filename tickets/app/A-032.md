## Context

Range cannons can be earned through mastery, but the `nine_pounder` is `unlock.kind: chest` and no
code grants chest cannons. `rollChest` returns only rarity and coins and is never called by live
settlement. A-008's in-memory ledger also cannot make a Harbor purchase atomic or survive
relaunch; A-041 supplies the durable receipt contract this ticket must consume.

## Planning Decisions

- **[locked-decision]** Range cannons remain mastery rewards. A chest may not bypass that progression.
- **[locked-decision]** A rare chest grants the missing chest-only cannon before falling back to its tuned
  coin result; this uses the existing rarity roll without inventing a second reward-weight table.
- **[locked-decision]** Duplicate cannon rewards degrade deterministically to the rolled coin
  result. Settlement is once per duel and the UI receives only what was actually written.
- **[locked-decision]** A rare missing-cannon result grants the cannon and `0` chest coins; its
  rolled coins remain recorded only as the duplicate fallback. Common/uncommon results and rare
  results after ownership grant exactly the rolled coins. The existing duel purse is separate.
- **[locked-decision]** Duel idempotency key is `duel:<duelId>` with the canonical duel seed.
  Harbor key is `purchase:<nextPurchaseSequence>` and its seed is a stable hash of that key, never
  a screen-supplied reroll. Reusing a committed key returns the persisted receipt unchanged.
- **[locked-decision]** `settleDuelRewards` and `settleStoreChest` compute the complete next Captain
  first, then call `replaceCaptain` exactly once with no `await` between read and commit. Any
  validation/roll failure, insufficient balance, or stale purchase sequence commits nothing.

## Acceptance Criteria

- **AC-1**: Given a finished winning duel, when rewards settle, then exactly one seeded chest roll
  is consumed and its receipt is persisted under `duel:<duelId>` in the same Captain replacement
  as purse, mastery, win/rank, and inventory.
- **AC-2**: Given the same seed and ownership state, when settlement is replayed, then the chest
  result is identical and a second observation grants nothing.
- **AC-3**: Given a rare result and an unowned chest-only cannon, when settled, then that cannon is
  added once, marked unseen, and included in the applied reward projection.
- **AC-4**: Given no missing chest-only cannon, when a cannon-granting result settles, then it
  degrades to the exact tuned coin drop and never duplicates ownership.
- **AC-5**: Given every catalog cannon and grade band, when acquisition policy is audited, then it
  has at least one attainable path and only the two documented older-band placement exceptions
  have multiple paths; all other cannons remain starter-only, range-only, or chest-only.
- **AC-6**: Given defeat, when rewards settle, then the small purse still applies but no victory
  chest is rolled.
- **AC-7**: Given sufficient coins and the current purchase sequence, when a store chest is
  settled, then debit, sequence increment, receipt, coins/cannon, and NEW inventory state commit
  in one Captain replacement; a repeated old sequence returns the exact receipt without another
  debit or roll.
- **AC-8**: Given insufficient coins, a stale/future sequence, injected roll failure, invalid
  price, or invalid receipt, when store settlement is attempted, then Captain is deeply unchanged
  and no receipt is created.
- **AC-9**: Given a committed duel or purchase receipt and a relaunch, when the same key is
  observed again, then the persisted receipt is returned byte-equivalently and no reward, debit,
  mastery, or rank transition is repeated.

## Test Plan

- Unit/property (deterministic): seeded rolls, exact rare/fallback semantics, key grammar/hash,
  sequence ordering, idempotence across relaunch, injected failures, win/loss, and complete
  band-specific catalog path audit.
- Integration: one-spy `replaceCaptain` proof for duel/store commits; player store, retained
  receipt, and victory projection agree exactly.
