## Context

**This ticket is retrospective, and that is the point.** `src/stores/duel.ts` is 295 lines of
shipped, working reducer — phase machine, per-skill tally, rival volley, settle — and `app/duel.tsx`
is the screen that drives it. Between them they are the single largest item on the MVP checklist,
and **no ticket specifies either.** A-008 has six criteria and all six are about what happens to the
captain _after_ the duel ends; nothing anywhere says what a duel is.

The consequence is not hypothetical. The adversarial plan review found that `app/duel.tsx` had
shipped reading `resolvePlacement('k_1')` — a hardcoded grade band that handed a grade 4–5 player
K-1 cannons and made "two starter cannons that are a real choice" false for two of the three bands.
It was found by reading, because there was no criterion for it to fail.

**Expected implementation delta: zero.** The criteria below are written against what _should_ be
true of the shipped machine, and most or all will pass on the first run. That is the intended
outcome. The deliverable is not a code change; it is that checklist item 5 stops being unspecified
and starts being regression-protected before A-014 and A-015 edit this reducer.

Interfaces it consumes, all already wired:

```ts
resolveShot({ cannon, correct, elapsedMs, rng }): readonly [ShotOutcome, Rng]; // @engine/duel/damage
computeCoinPayout({ won, totalAnswers, correctAnswers, perfectShots }): number; // @engine/economy
PLAYER_HULL, ENEMY_HULL_BY_ISLAND, CHOICE_COUNT, PERFECT_SHOT_TIMER_FRACTION; //  @engine/tuning
```

## Planning Decisions

- **The reducer is presentation state, not the engine's `DuelState`.** T-013/T-020 own the canonical
  duel state on the engine track; this reducer decides what is on screen and for how long. The
  criteria below deliberately assert _delegation_ — that damage comes from `resolveShot` and the
  payout from `computeCoinPayout` — rather than re-deriving the engine's own numbers here, which
  would put the same rule in two places with two owners.
- **"A real choice" is asserted as the reducer honouring the picked gun, not as a balance claim.**
  The two starters share a skill and a timer and differ in risk profile: `swivel_gun` is
  `reliable`, 8–12; `culverin` is `volatile`, 4–16. Whether that spread is _interesting_ is a
  content question owned by the catalog and by T-029. What this ticket can and does pin is that the
  gun the player tapped is the gun that fires, on its own skill, inside its own damage band.
- **Owner-visible observation, not asserted here:** `culverin` ships `recoilDamage: 0`, so the
  volatile starter currently has no downside beyond variance, and the reducer's careful
  `damageToSelf` recoil path is dead at K-1. That is a catalog tuning question, not a duel-core
  defect, and it is recorded rather than silently pinned by a test.

## Acceptance Criteria

- **AC-1**: Given a captain with two equipped starters, when either is picked, then the question
  that follows is drawn for _that cannon's_ `skill` and the volley that resolves is priced from
  _that cannon's_ own `damageMin`/`damageMax` band — the tray never substitutes another gun, and the
  screen's tray is built from `captain.equippedCannons` and from nothing else.
- **AC-2**: Given any transition into the `question` phase, when the state is inspected, then
  `question` is non-null and holds exactly `CHOICE_COUNT` choices, with `answer` appearing among
  them exactly once.
- **AC-3**: Given the same cannon, seed and correctness, when the same answer is submitted at a
  smaller `elapsedMs`, then `damageToEnemy` is never lower than at a larger one, and an answer
  inside `PERFECT_SHOT_TIMER_FRACTION` of the timer sets `perfectShot` — the shot is aimed by
  speed, and every number in it comes from `resolveShot`, none from this layer.
- **AC-4**: Given a wrong answer, when the volley resolves, then the rival's hull is unchanged, the
  turn passes to the rival, and any damage the player takes is exactly the engine's
  `outcome.damageToSelf` — being wrong costs the turn, never permission to play.
- **AC-5**: Given any phase and any action, when the reducer is applied, then the result is either
  an unchanged state or a state whose `phase` is a declared `DuelPhase`; and every phase other than
  `victory` and `defeat` has an exit — a `PHASE_DURATION_MS` entry, or a player input that leaves
  it. This is the soft-lock catastrophe class in ARCHITECTURE §9 and it is asserted by an
  exhaustive walk of (phase × action), not by reading the switch.
- **AC-6**: Given a volley that takes the rival's hull to zero, when it resolves, then the duel ends
  in `victory` with no rival counter-volley after the sinking shot; given the player's hull reaching
  zero, it ends in `defeat`; and neither hull is ever negative at any point in any action log.
- **AC-7**: Given the same seed and the same action log, when the duel is replayed, then every
  intermediate state is deeply equal to the first run — the reducer reads no clock and no ambient
  randomness, and `elapsedMs` arrives as data.
- **AC-8**: Given any action log, when the state is inspected, then the per-skill tally's `asked`
  values sum to `asked` and its `correct` values sum to `right` — the mastery meter and the
  scoreboard can never tell a child two different stories.
- **AC-9**: Given a finished duel, when `RESET` is dispatched, then the new state has a `duelId`
  different from the previous one, both hulls at full, phase `select`, and an rng stream carried
  forward from the old one — so "fight again" is a duel the reward ledger has not already settled.

## Test Plan

- Unit (deterministic): AC-1 through AC-4, AC-6, AC-9 against `duelReducer` and `initialDuelState`.
  The reducer is pure and seeded, so all of it runs headless with no component harness.
- Property (deterministic): AC-5 as an exhaustive sweep of every `DuelPhase` × every `DuelAction`;
  AC-7 and AC-8 over randomly generated action logs at fixed seeds. AC-6's "never negative" is a
  property over the same logs — a hand-picked case cannot cover a hull arithmetic bug.
- Visual (design-fidelity, NOT frozen): the eleven phase panels against the named boards at 375pt
  and at 360×640 / 390×844 / 430×932, screenshot evidence attached. **Posture-gated deferral** — no
  component-test harness exists for the app layer (`.tdd-swarm/posture.md`).
