## Context

The screens were built from a 375pt phone reference and mostly scale from raw window width. That
protects narrow phones but can make typography, art, tap controls, and navigation sheets stretch
without limit on iPad and desktop web. The release needs intentional large-screen composition, not
a phone UI enlarged to fill every pixel.

A-042 owns the immediate onboarding text/launch hotfix and overlaps one screen, so this ticket may
freeze tests and complete its audit in parallel but implementation begins only after A-042 lands.

## Planning Decisions

- **[locked-decision]** Viewports are classified by width: compact `< 600`, tablet `600–1023`, and
  desktop `>= 1024`. Rotation changes the class from measured width; platform sniffing is forbidden.
- **[locked-decision]** Compact behavior stays pixel-compatible with the shipped phone flow.
- **[locked-decision]** Reading/form surfaces (onboarding, name/flag, gun deck, range controls) are
  centered and width-capped at 760pt. World/action surfaces (chart and duel) are centered and
  width-capped at 1180pt so they can use landscape space without unbounded stretching.
- **[locked-decision]** Tablet/desktop outer gutters are at least 24/32pt respectively. Width
  capping never reduces the existing 64pt child-facing control height or makes text smaller than
  the compact design.
- **[locked-decision]** One shared responsive frame owns centering, width caps, and background
  gutters. Screens select a `reading` or `world` surface; they do not each invent breakpoints.
- **[locked-decision]** No hover-only action, mouse-only interaction, orientation lock, or separate
  desktop route is introduced.

## Acceptance Criteria

- **AC-1**: Given widths on both sides of 600 and 1024, when layout is resolved, then exactly one
  compact/tablet/desktop class is returned from width alone with deterministic boundary behavior.
- **AC-2**: Given compact viewports from 320–599pt, when either surface is resolved, then content
  uses the available width minus the existing compact gutters and preserves current scale/tap
  behavior.
- **AC-3**: Given tablet or desktop widths, when a reading surface is resolved, then it is centered,
  never exceeds 760pt, and retains at least the class gutter on each side.
- **AC-4**: Given tablet or desktop widths, when a world surface is resolved, then it is centered,
  never exceeds 1180pt, and retains at least the class gutter on each side.
- **AC-5**: Given every child-facing route, when its source is inspected, then it consumes the one
  shared responsive frame with the correct reading/world role and introduces no local width
  breakpoint or platform-specific fork.
- **AC-6**: Given iPad portrait, iPad landscape, and 1440×900 desktop evidence, when the demo flow
  is exercised, then no child-facing copy/control is clipped or horizontally scrolled, controls
  remain at least 64pt, and the chart/duel stay visually centered.

## Test Plan

- Unit/property (deterministic): sweep viewport widths/heights through both boundaries and extreme
  desktop widths; assert class, finite geometry, caps, centering, gutters, and compact compatibility.
- Source contract (deterministic): every route uses `ResponsiveFrame` with the ticket-owned surface
  role and contains no new breakpoint literals/platform branch.
- Visual release evidence (required): screenshots at 768×1024, 1024×768, 1366×1024, and 1440×900
  across launch/onboarding, chart, duel, range, and gun deck.
