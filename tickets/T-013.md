## Context

The vocabulary of the duel machine, plus its constructor. T-020 owns the transitions; this
ticket owns the shapes they move between — split out because the type surface is consumed by
three later tickets (T-018 opponents, T-020 reducer, T-024 invariants + replay proof) and must be
settled before any of them starts.

**Phases** (exactly ARCHITECTURE.md §4.2, no additions):

```ts
export const DUEL_PHASES = [
  'countdown',
  'playerChoose',
  'reload',
  'resolvePlayer',
  'rivalTurn',
  'resolveRival',
  'victory',
  'defeat',
] as const;
```

**`DuelState` is a discriminated union on `phase`, over a common core:**

```ts
interface DuelCore {
  readonly seed: number;
  readonly rng: Rng; // PRNG state travels in the state
  readonly turnToken: number; // increments once per turn handoff
  readonly volleyNumber: number; // 1-based, increments per player volley
  readonly islandId: IslandId;
  readonly playerHull: number; // clamped >= 0
  readonly enemyHull: number; // clamped >= 0
  readonly enemyMaxHull: number;
  readonly playerLoadout: readonly CannonId[]; // >= 1 entry
  readonly rivalLoadout: readonly CannonId[]; // >= 1 entry
  readonly recentTemplateIds: readonly string[]; // most-recent-first
  readonly actionLog: readonly ActionLogEntry[];
  readonly tally: DuelTally;
  readonly templatesBySkill: Readonly<Partial<Record<SkillId, readonly Template[]>>>;
}
```

Per-phase extras: `reload` adds `{ cannonId, question, timerMs }`; `resolvePlayer` adds
`{ cannonId, outcome: ShotOutcome }`; `resolveRival` adds
`{ volley: RivalVolley, damageToPlayer: number }`; `victory` and `defeat` add
`{ result: DuelResult }`. `countdown`, `playerChoose`, and `rivalTurn` add nothing.

**Supporting shapes:**

```ts
export interface ActionLogEntry {
  // ARCHITECTURE.md §4.2, verbatim fields
  readonly actor: 'player' | 'rival';
  readonly cannonId: CannonId;
  readonly correct: boolean;
  readonly elapsedMs: number;
}
export interface RivalAction {
  readonly cannonId: CannonId;
} // what Opponent.chooseAction returns
export interface RivalVolley {
  // the RIVAL_ACTION event payload
  readonly cannonId: CannonId;
  readonly correct: boolean;
  readonly elapsedMs: number;
}
export interface RivalView {
  // what an Opponent is allowed to see
  readonly volleyNumber: number;
  readonly playerHull: number;
  readonly enemyHull: number;
  readonly enemyMaxHull: number;
  readonly rivalLoadout: readonly CannonId[];
  readonly playerRecentCorrect: readonly boolean[];
}
export interface DuelTally {
  readonly correctAnswers: number;
  readonly totalAnswers: number;
  readonly perfectShots: number;
  readonly bySkill: Readonly<
    Partial<Record<SkillId, { readonly correct: number; readonly attempts: number }>>
  >;
}
export interface DuelResult {
  readonly won: boolean;
  readonly tally: DuelTally;
  readonly volleys: number;
}

export type DuelEvent =
  | { readonly type: 'CANNON_SELECTED'; readonly cannonId: CannonId }
  | { readonly type: 'ANSWER_CHOSEN'; readonly choiceIndex: number; readonly elapsedMs: number }
  | { readonly type: 'TIMER_EXPIRED' }
  | { readonly type: 'ANIMATION_DONE' }
  | { readonly type: 'RIVAL_ACTION'; readonly volley: RivalVolley };

export interface DuelConfig {
  readonly seed: number;
  readonly islandId: IslandId;
  readonly playerLoadout: readonly CannonId[];
  readonly rivalLoadout: readonly CannonId[];
  readonly templatesBySkill: Readonly<Partial<Record<SkillId, readonly Template[]>>>;
}
export function createDuelState(config: DuelConfig): DuelState; // phase 'countdown'
export function isTerminalPhase(phase: DuelPhase): boolean; // victory | defeat
export function toRivalView(state: DuelState): RivalView;
```

## Planning Decisions

- `locked-decision` — the eight phases, the five event types, and the four action-log fields are
  taken verbatim from ARCHITECTURE.md §4.2. No phase is added here; Double-Shot's phase is
  T-022's to add, deliberately, so the base machine ships first.
- `proposed` — `RivalAction`, `RivalVolley`, and `RivalView` live in `duel/types.ts` rather than
  in `opponents/`. `DuelEvent` must reference `RivalVolley`, and `RivalView` is a projection of
  `DuelState`; putting them in `opponents/` would create an import cycle.
- `proposed` — `RivalAction` is `{ cannonId }` only, matching ARCHITECTURE.md §4.2's
  `chooseAction(view): Promise<RivalAction>`; correctness and elapsed time come from the same
  document's `produceAnswer`. The store driver combines the two into one `RivalVolley` and
  dispatches a single `RIVAL_ACTION` event, which is what "`rivalTurn` collapses the rival's
  choose+reload+answer into one opponent-driven step" means at the reducer boundary.
- `proposed` — the whole PRNG state (`rng`) and the template pool reference live in the state /
  config rather than being closed over, so `DuelState` is a plain JSON value. This is what makes
  mid-duel kill/relaunch (PLAN.md MVP checklist) and the T-024 replay proof possible.
- `proposed` — `templatesBySkill` is **injected via `DuelConfig` and then carried in the state**,
  not imported from the content registry. Carrying it keeps `duelReducer(state, event)` to the
  two-argument signature ARCHITECTURE.md §4.2 specifies, keeps a serialised duel
  self-contained for mid-duel relaunch, and keeps the duel machine independent of T-019 and
  testable with two fixture templates. Templates are plain JSON, so the state stays serialisable.
- `proposed` — `RivalView` exposes only hulls, volley number, the rival's own loadout, and the
  player's recent correctness. An opponent must not see the current question or the PRNG, or a
  future remote opponent becomes a cheat vector (ARCHITECTURE.md §4.2: the same interface a
  network player fills).
- `proposed` — `DuelTally.bySkill` accumulates per-skill correct/attempt counts so the store can
  apply half-rate mastery after the duel. The reducer does **not** call `mastery.ts`; keeping
  that dependency out avoids coupling the machine to progression.
- `locked-decision` — `playerHull` starts at `PLAYER_HULL` (100) every duel and is never
  persisted (ARCHITECTURE.md §4.3, PLAN.md "Your hull resets after every duel").
- `proposed` — **this file is designed to be extended once, by T-022.** `ActionLogEntry` is
  specified as a closed set of _required_ fields that tolerates documented optional additions,
  and the DoD forbids tests from deriving phase/event lists from the exported unions. Both exist
  so T-022's Double-Shot lands as a patch rather than superseding this ticket's frozen tests.

## Acceptance Criteria

- **AC-1**: Given `DUEL_PHASES`, when inspected, then it contains exactly the eight phase names
  from ARCHITECTURE.md §4.2 in that order, with no duplicates and no extras.
- **AC-2**: Given a valid `DuelConfig`, when `createDuelState` is called, then the result's
  `phase` is `"countdown"`, `playerHull === PLAYER_HULL` (100),
  `enemyHull === enemyMaxHull === ENEMY_HULL_BY_ISLAND[config.islandId]`, `volleyNumber === 1`,
  `turnToken === 0`, `actionLog` is empty, `recentTemplateIds` is empty, and every `tally`
  counter is `0` with an empty `bySkill`.
- **AC-3**: Given the same `DuelConfig`, when `createDuelState` is called twice, then the two
  states are deeply equal — including `rng`, which is derived solely from `config.seed`.
- **AC-4**: Given two configs differing only in `seed`, when both are constructed, then their
  `rng` values differ.
- **AC-5**: Given a `DuelConfig` with an empty `playerLoadout` or an empty `rivalLoadout`, or a
  loadout naming a `CannonId` absent from the catalog, or an `islandId` with no
  `ENEMY_HULL_BY_ISLAND` entry, when `createDuelState` is called, then it throws an `Error`
  naming the offending field.
- **AC-6**: Given a `DuelState` in each of the eight phases, when round-tripped through
  `JSON.parse(JSON.stringify(state))`, then the result is deeply equal to the original — no
  functions, no `Map`/`Set`, no `undefined`-valued keys, no class instances.
- **AC-7**: Given `isTerminalPhase`, when called for each phase, then it returns `true` for
  exactly `"victory"` and `"defeat"` and `false` for the other six.
- **AC-8**: Given a `DuelState`, when `toRivalView` is called, then the returned object's keys
  are exactly those of `RivalView` — it contains no `rng`, no `seed`, no `question`, and no
  `actionLog`.
- **AC-9**: Given a state whose `actionLog` holds player and rival entries, when
  `toRivalView(state).playerRecentCorrect` is read, then it lists the `correct` values of the
  player entries only, most-recent-first.
- **AC-10**: Given a `DuelState` narrowed by `state.phase === 'reload'`, when compiled, then
  `state.question` and `state.cannonId` are accessible without a cast; and given a state
  narrowed to `'playerChoose'`, then accessing `state.question` is a **type error**. The test
  asserts this with a `// @ts-expect-error` line, so the discrimination is enforced at build time.
- **AC-11**: Given `ActionLogEntry`, when constructed, then its **required** fields are exactly
  `actor`, `cannonId`, `correct`, `elapsedMs`, each present and correctly typed, and a value
  carrying only those four parses, serialises, and round-trips unchanged. A later ticket may add
  **optional** fields (T-022 adds `doubleShot?`); any such field must be _omitted_ when absent,
  never set to `undefined`, so AC-6's JSON round-trip stays exact. The test asserts the four
  required fields positively and asserts omission-not-undefined; it must **not** assert
  `keyof ActionLogEntry` exactness, which would pre-break T-022 in wave 6.
- **AC-12**: Given a `DuelState`, when any attempt is made to mutate `state.actionLog` or
  `state.playerLoadout`, then it fails under `readonly` typing (asserted with
  `// @ts-expect-error`) — the state is treated as immutable by contract.

## Wave-1 contract note — seeding `createRng` (added by the orchestrator 2026-07-28)

`createRng` (T-001, AC-15) **throws `RangeError` on any seed that is not a finite integer in
`[-0xffffffff, 0xffffffff]`.** It no longer silently truncates. Anything deriving a seed from a
wide source — `Date.now()`, a hash, a composed id — must mask before calling:

```ts
const rng = createRng(rawSeed >>> 0);
```

This was a deliberate fix: `NaN`, `-0.5`, and `2 ** 33` all previously collapsed to `{state: 0}`,
aliasing three distinct seeds onto one stream in the module whose whole purpose is
replay-from-seed. Raised as an advisory by the T-001 code review.
