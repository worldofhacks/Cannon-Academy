## Context

ARCHITECTURE.md makes a specific, falsifiable claim: **seed + action log = an exactly
reconstructable duel.** Two future features rest on it — ghost-captain async PvP and
server-validated payouts (§13) — and neither is built. This ticket makes the claim a test, now,
while the machine is small enough that a violation is cheap to fix.

```ts
export interface ReplayResult {
  readonly finalState: DuelState;                 // terminal: victory | defeat
  readonly states: readonly DuelState[];          // every state, in order
}
export function replayDuel(input: {
  readonly config: DuelConfig;                    // carries the seed
  readonly actionLog: readonly ActionLogEntry[];
}): ReplayResult;
```

**Reconstruction.** Start from `createDuelState(config)`, then for each log entry in order:

- `actor: 'player'` → `ANIMATION_DONE` if the current phase is `countdown` or `resolveRival`,
  then `CANNON_SELECTED { cannonId }` (or `DOUBLE_SHOT_SELECTED` when the entry has
  `doubleShot: true`), then `ANSWER_CHOSEN { choiceIndex, elapsedMs }`, then `ANIMATION_DONE`.
- `actor: 'rival'` → `RIVAL_ACTION { volley: { cannonId, correct, elapsedMs } }`, then
  `ANIMATION_DONE`.

**The log records `correct`, not `choiceIndex`.** Replay therefore derives the index: the
question's `correctIndex` when `correct` is `true`, and otherwise the **lowest index that is not
`correctIndex`** — a fixed rule, so replay is deterministic. This is sound because nothing
downstream of grading depends on *which* wrong choice was tapped: damage is a function of the
PRNG, the cannon, correctness, and `elapsedMs`, all of which the log or the seed supplies.

## Planning Decisions

- `proposed` — the lowest-non-correct-index rule for reconstructing a wrong tap. The alternative
  was widening `ActionLogEntry` to carry `choiceIndex`, which grows the persisted `duels/{id}`
  document for no behavioural gain. AC-4 pins that the choice of index does not affect the
  outcome, which is what makes the shortcut safe rather than merely convenient.
- `proposed` — `replayDuel` returns every intermediate state, not just the final one. A ghost
  captain needs the per-turn sequence to drive the `Opponent` interface (ARCHITECTURE.md §13),
  and the state list is what makes AC-2's step-by-step equality check possible.
- `proposed` — replay dispatches through the **real** `duelReducer`. A separate reconstruction
  path would be a second implementation of the rules and would drift; the whole point is that
  the same machine, same seed, and same inputs land in the same place.
- `proposed` — a log that runs out before a terminal phase is an error, not a partial replay.
  A truncated log means the recorded duel is corrupt; silently returning a mid-duel state would
  let a future server-side payout check pass on incomplete evidence.
- `deferred` — the ghost-captain `Opponent` adapter that would let a replayed log *drive* a live
  duel (ARCHITECTURE.md §13). Documented, not built; this ticket delivers the reconstruction
  primitive it would need.

## Acceptance Criteria

- **AC-1**: Given a duel driven to `victory` through the reducer, when its `config` and the final
  state's `actionLog` are passed to `replayDuel`, then `finalState` is deeply equal to the
  original final state — including `playerHull`, `enemyHull`, `rng`, `turnToken`,
  `volleyNumber`, `tally`, `actionLog`, and `result`.
- **AC-2**: Given the same duel, when the replay's `states` array is compared with the states the
  original dispatch sequence produced, then the two sequences have the same length and are
  element-wise deeply equal.
- **AC-3**: Given a duel driven to `defeat` — including at least one volatile misfire that
  damaged the player — when replayed, then `finalState` is deeply equal to the original, and
  `finalState.result.won` is `false`.
- **AC-4**: Given a duel in which the player tapped a wrong choice whose index was **not** the
  lowest non-correct index, when replayed, then `finalState` is still deeply equal to the
  original — which wrong choice was tapped provably does not affect the outcome.
- **AC-5**: Given a duel containing at least one Perfect Shot and one Double-Shot turn, when
  replayed, then `finalState` is deeply equal to the original, and the replayed states record the
  same `perfectShot` and `doubleShot` flags at the same positions.
- **AC-6**: Given a duel containing a `TIMER_EXPIRED` turn, when replayed from its log entry
  (`correct: false`, `elapsedMs === timerMs`), then `finalState` is deeply equal to the original.
- **AC-7**: Given a config whose `seed` differs from the one the log was recorded under, when
  replayed, then `finalState` is **not** deeply equal to the original — the test proves the
  reconstruction genuinely depends on the seed and is not accidentally seed-independent.
- **AC-8**: Given an `actionLog` that ends before a terminal phase is reached, when replayed,
  then it throws an `Error` naming the phase it stopped in and the number of entries consumed.
- **AC-9**: Given an `actionLog` whose entries are out of order — a `rival` entry where a
  `player` entry is due — when replayed, then it throws an `Error` naming the offending entry
  index.
- **AC-10**: Given an `actionLog` entry naming a `cannonId` outside the relevant loadout, when
  replayed, then it throws an `Error` naming the offending entry index, rather than silently
  no-op'ing forever.
- **AC-11**: Given the same `config` and `actionLog`, when `replayDuel` is called 20 times, then
  all 20 results are deeply equal, and the input `actionLog` array is unmutated.
- **AC-12**: Given a duel of 6 player volleys, when the log is serialised with `JSON.stringify`,
  transported as a string, parsed back, and replayed, then `finalState` is deeply equal to the
  original — the log is a valid wire format for the `duels/{id}` document (ARCHITECTURE.md §5).
- **AC-13**: Given 50 seeded duels driven by pseudo-random but valid event streams to a terminal
  phase, when each is replayed from its own log, then all 50 reconstruct exactly — the claim
  holds across the state space, not just on a hand-built example.

## Test Plan

- Unit (deterministic): AC-1, AC-2, AC-3 — victory and defeat reconstruction, both final-state
  and step-by-step.
- Unit (deterministic): AC-4, AC-5, AC-6 — the three cases where reconstruction could plausibly
  diverge: an unrecorded wrong-choice index, the Perfect Shot / Double-Shot modifiers, and a
  timeout.
- Unit (deterministic): AC-7 — the negative control. Without it, a replay that ignored the log
  entirely could still pass every other criterion.
- Unit (deterministic): AC-8, AC-9, AC-10 — corrupt-log failure modes, each a named throw.
- Unit (deterministic): AC-11, AC-12 — determinism, non-mutation, and JSON wire round-trip.
- Unit (deterministic): AC-13 — a 50-duel seeded sweep over varied event streams.
- Eval: none.
