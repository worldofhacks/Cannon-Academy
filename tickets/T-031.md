## Context

Two statements in ARCHITECTURE §4.3 are not satisfiable by the shipped constants:

```
ARCHITECTURE:202  "perfectShot → +1 bonus ball"
tuning.ts:89      PERFECT_SHOT_BONUS_DAMAGE = 1      <- +1 DAMAGE, not a ball
ARCHITECTURE:206  "Damage renders as N cannonball arcs, so the roll reads as shot spread"
tuning.ts:86      BASE_BALLS_PER_VOLLEY = 1          <- one arc; no spread can read
```

The external design review caught the first: a prototype showing a "+1 BALL" chip advertises a
mechanic the engine does not implement. The T-004 code review independently flagged the second as a
Minor.

**This must resolve before T-008 (wave 3) builds the damage model**, which would otherwise bake in
whichever reading it happens to infer.

## Planning Decisions

- `proposed` (orchestrator, 2026-07-28) — **damage is scalar; balls are presentation.**
  - `PERFECT_SHOT_BONUS_DAMAGE` stays `+1` **damage**.
  - `BASE_BALLS_PER_VOLLEY` is reclassified as a **rendering constant the engine ignores** — how
    many arcs to draw for one volley. Damage does not subdivide across it, and drawing an extra arc
    adds no damage.
  - ARCHITECTURE §4.3's "+1 bonus ball" wording is **corrected** to "+1 damage, celebrated with an
    extra cannonball arc", so doc and code agree.

  **Rationale:** the bonus was never where the reward lives. On the Swivel (8–12), a fast answer
  already biases the roll from 8–10 up to 11–12 through `QUALITY_WEIGHT` — roughly a **60% swing**,
  and that is what a child actually feels. The `+1` is garnish. Calling it a "ball" implies a
  mechanic that does not exist and sets a designer up to advertise it in the UI.

- `open-question` — the arc count for legibility is the designer's call, not the engine's. Under
  this ruling, choosing three arcs so the spread reads is a pure presentation change with no engine
  impact.

## Acceptance Criteria

## Second defect, added 2026-07-28 — the derived `QUALITY_WEIGHT` bound is too loose

The T-008 Test Agent measured the bound this project derived in wave 2 against T-008's **actual**
AC-16 assertion, rather than against the formula the derivation used. They disagree:

```
T-004 freezes:   QUALITY_WEIGHT > 7/12 ≈ 0.5833
Measured bite:   0.5834 FAILS · 0.58 FAILS · 0.55 FAILS · 0.40 FAILS · 0.001 FAILS
                 real threshold is W <= 0.6 fails, 0.601+ passes
```

**Cause:** the closed-form derivation dropped the `ceil` in
`lower = min(ceil(lowerRaw), damageMax)`, and that rounding is precisely what discretises the
effect. Binding cannon is `twelve_pounder`/`mortar` (span 10): at `W = 0.6` the expected mean gap
is exactly `1.0 = 0.10 × span` — a knife edge sampling noise flips either way.

**Nothing is broken today.** The shipped `0.7` clears the real threshold by ≥ 0.5 damage (~25
standard errors at n = 20,000). But a future "soften the curve to 0.6" would **pass T-004 and fail
T-008** — which is exactly the split-brain L-018 was written to prevent, reappearing because the
derivation itself was subtly wrong.

- **AC-6**: Given `__tests__/engine/tuning.test.ts`, then the `QUALITY_WEIGHT` effect-size bound
  asserts `> 0.6`, not `> 7/12`, and the comment records that the earlier bound omitted the `ceil`
  discretisation and was therefore unsound.
- **AC-7**: Given `QUALITY_WEIGHT`'s shipped value, then it is unchanged at `0.7` — this tightens a
  bound, it does not retune the game.
- **AC-8**: Given the full repo suite, then it passes; the tightened bound must be **verified
  against T-008's actual AC-16 assertion**, not re-derived in closed form. Run the measurement.
