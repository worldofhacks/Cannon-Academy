## Context

This ticket establishes the **single type vocabulary** the whole swarm builds on. Every later
ticket imports its ids and shapes from here, so it is deliberately the first thing built and it
must not be edited afterwards except by a follow-up ticket.

Two files, one concern (the shared vocabulary):

1. `src/content/schemas.ts` — zod schemas for every bundled catalog, with the TypeScript types
   derived by `z.infer` so there is exactly one source of truth. Catalogs are JSON (no
   compile-time types), which is precisely why runtime validation is the contract.
2. `src/engine/questions/types.ts` — engine-side types that are *produced*, not authored:
   a generated `Question`, its `Choice` list, and the typed generation error.

**Id sets, derived from PLAN.md's armory table and island list — these are exhaustive:**

- `GradeBand`: `k_1`, `g2_3`, `g4_5` (PLAN.md grade picker).
- Numeric grades: K is `0`, grades 1–5 are `1`–`5`.
- `SkillId`: `add_within_10`, `add_within_20`, `sub_within_20`, `place_value_compare`,
  `mult_facts`, `two_step_add_sub`, `div_facts`, `fractions_int`, `multi_digit_order_ops`.
- `CannonId`: `swivel_gun`, `culverin`, `six_pounder`, `chain_shot`, `nine_pounder`,
  `twelve_pounder`, `mortar`, `double_broadside`, `powder_keg`, `long_nine`.
- `IslandId`: `port_sumwich`, `isla_products`, `quotient_cove`, `fraction_reef`, `grandline`.
- `RankId`: `cadet`, `ensign`, `captain`, `commodore`, `fleet_legend`.
- `Temperament`: `reliable`, `standard`, `volatile`.
- `ChestRarity`: `common`, `uncommon`, `rare` (see Planning Decisions).

**Required shapes** (field names are the contract; T-006 authors the data against them):

```ts
skillSchema    { id: SkillId; displayName: string; minGrade: 0..5; maxGrade: 0..5; symbolicOnly: boolean }
templateSchema { id: string; skill: SkillId; text: string;
                 params: Record<string, [int, int]>; constraints?: string[];
                 answerExpr: string; distractors: string[] (>=3);
                 isWordProblem?: boolean; readAloud?: boolean;
                 difficulty?: 1 | 2 | 3 }        // insurance — see Planning Decisions
cannonSchema   { id: CannonId; displayName: string; skill: SkillId;
                 damageMin: int>0; damageMax: int>0; temperament: Temperament;
                 recoilDamage: int>=0; timerMs: int>0; minGrade: 0..5; maxGrade: 0..5;
                 unlock: { kind: 'starter' } | { kind: 'range'; island: IslandId; tier: int>=1 } | { kind: 'chest' } }
islandSchema   { id: IslandId; displayName: string; order: int>=0;
                 rangeSkills: SkillId[]; unlocksCannons: CannonId[]; requiresIsland?: IslandId }
rankSchema     { id: RankId; displayName: string; tier: int>=0; minWins: int>=0 }
crewSchema     { id: string; displayName: string; role: string }
```

**Exported id-array names — locked by the orchestrator, 2026-07-27.** Every id union has a
companion `as const` array; the ticket previously said "the corresponding exported array"
without naming it, which left each consumer free to guess a different name. These names are
now binding, and T-009 in particular imports `CHEST_RARITIES`:

```ts
SKILL_IDS · CANNON_IDS · ISLAND_IDS · RANK_IDS · GRADE_BANDS · TEMPERAMENTS · CHEST_RARITIES
```

**Engine question types** (`src/engine/questions/types.ts`) — these are *produced* by T-007, not
authored, and five downstream tickets assert on their fields. The field sets are the contract:

```ts
interface Choice   { readonly value: number; readonly label: string }
interface Question {
  readonly templateId: string;
  readonly skill: SkillId;
  readonly text: string;                                  // fully rendered, no `{…}` left
  readonly params: Readonly<Record<string, number>>;       // the sampled values
  readonly choices: readonly Choice[];                     // exactly CHOICE_COUNT (4)
  readonly correctIndex: number;                           // 0..3
  readonly isWordProblem: boolean;                         // normalised — never undefined
  readonly readAloud: boolean;                             // normalised — never undefined
}
```

## Planning Decisions

- `proposed` — zod schemas are the single source of truth; TS types are `z.infer`. The engine
  imports types from `@content/schemas`. This is legal under the engine-purity lint (only
  React/RN/Expo/Firebase are banned) and avoids a second, drifting type declaration.
- `proposed` — `symbolicOnly` lives on the **skill**, per ARCHITECTURE.md §4.1 ("a per-skill
  `symbolicOnly` flag"), while `isWordProblem` lives on the **template**. The cross-check
  between them is enforced in T-019's golden suite.
- `proposed` — `recoilDamage` is a separate numeric field rather than being implied by
  `temperament`. See the Culverin open question in T-006.
- `proposed` — `ChestRarity` has exactly three tiers. PLAN.md says "drops a chest on a rarity
  roll" and never names the tiers or the count; three is the smallest set that makes "rarity"
  meaningful and gives T-009's weight-ordering test something to assert. **Flagged as an
  open question in `.tdd-swarm/traceability.md`.**
- `proposed` — `isWordProblem` and `readAloud` are optional and default to `false` when absent,
  so ~100 symbolic templates need not spell them out. Under `exactOptionalPropertyTypes` these
  infer as `prop?: boolean | undefined`; consumers must use `t.isWordProblem === true`, never
  a bare truthiness check on a possibly-absent property.
- `open-question` — ARCHITECTURE.md §4.1 has `readAloud?: boolean` flagged for TTS on grade-2+
  word problems, but PLAN.md marks coach-card read-aloud as a day-4 stretch. The field is
  carried in the schema; nothing in this swarm consumes it.
- `proposed` — **`difficulty?: 1 | 2 | 3` is insurance, not a feature.** It is a single optional
  schema line that **nothing in this swarm reads or writes**: T-014/T-015/T-016 must not author
  it, and T-007 must not branch on it. Its only purpose is to keep open question 2.10 (what "a
  harder variant of the same skill" means for Double-Shot) from becoming a wave-1 schema edit.
  Without the field, answering 2.10 the other way supersedes T-022 *and* reopens this frozen
  file *and* ~72 authored templates *and* T-019's registry. With it, that answer becomes a
  T-022-local patch plus content authoring. This is not a locked decision and not a design
  commitment — if 2.10 resolves to "shortened timer", the field simply stays unused.
- `proposed` — the `Question` / `Choice` field sets above are pinned by AC-15 and AC-16 because
  T-007, T-013, T-017, T-020, and T-024 all assert on `templateId`, `params`, `isWordProblem`,
  and `Choice.label`. `questions/types.ts` is in **no** downstream ticket's `file_scopes`, so a
  thinner shape frozen here would block T-007 against a file it cannot edit.

## Acceptance Criteria

- **AC-1**: Given each of the id unions (`SkillId`, `CannonId`, `IslandId`, `RankId`,
  `GradeBand`, `Temperament`, `ChestRarity`), when the corresponding exported `as const` array
  is inspected, then it contains exactly the members listed in Context, in that order, with no
  duplicates.
- **AC-2**: Given a fully-populated valid template object, when `templateSchema.parse` is
  called, then it returns the object with `id`, `skill`, `text`, `params`, `constraints`,
  `answerExpr`, and `distractors` preserved unchanged.
- **AC-3**: Given a template whose `skill` is a string not in `SkillId`, when parsed, then
  `templateSchema.safeParse` returns `success: false` and the issue path is `["skill"]`.
- **AC-4**: Given a template with only 2 distractors, when parsed, then `safeParse` returns
  `success: false` — a four-choice question needs at least three distractors
  (ARCHITECTURE.md §4.1).
- **AC-5**: Given a template whose `params` value is `[3]`, `[1, 2, 3]`, or `[1.5, 4]`, when
  parsed, then `safeParse` returns `success: false` for each — params are inclusive
  **integer** pairs.
- **AC-6**: Given a template with `constraints`, `isWordProblem`, and `readAloud` all absent,
  when parsed, then `safeParse` returns `success: true` and none of those keys is present on
  the parsed object (they are omitted, not set to `undefined`).
- **AC-7**: Given a cannon object with `damageMax < damageMin`, when parsed, then `safeParse`
  returns `success: false`; given `damageMax === damageMin`, then it returns `success: true`.
- **AC-8**: Given a cannon with `temperament: "reliable"` and `recoilDamage: 3`, when parsed,
  then `safeParse` returns `success: false` — a reliable gun never punishes a miss
  (PLAN.md §The duel loop).
- **AC-9**: Given a cannon with `timerMs` of `0` or a negative value, or a non-integer, when
  parsed, then `safeParse` returns `success: false`.
- **AC-10**: Given a skill object with `maxGrade < minGrade`, when parsed, then `safeParse`
  returns `success: false`; given `minGrade: 0, maxGrade: 1`, then it returns `success: true`.
- **AC-11**: Given an island with `order: -1`, or a rank with `tier: -1`, or a rank with
  `minWins: -1`, when parsed, then `safeParse` returns `success: false` for each.
- **AC-12**: Given a cannon `unlock` of `{ kind: "range" }` with no `island`, when parsed, then
  `safeParse` returns `success: false`; given `{ kind: "starter" }`, then it returns
  `success: true`.
- **AC-13**: Given a `Question` value built with exactly four choices and `correctIndex` in
  `[0, 3]`, when passed to the exported `assertQuestion` guard, then it returns without
  throwing; given three choices, or five choices, or `correctIndex` of `-1` or `4`, then it
  throws a `QuestionGenerationError` with `code` `INVALID_QUESTION`.
- **AC-14**: Given `new QuestionGenerationError("msg", "CONSTRAINTS_UNSATISFIED")`, when
  inspected, then `instanceof Error` is `true`, `instanceof QuestionGenerationError` is `true`,
  `name` is `"QuestionGenerationError"`, and `code` is `"CONSTRAINTS_UNSATISFIED"`. The exported
  `QuestionGenerationCode` union is exactly `NO_TEMPLATE | CONSTRAINTS_UNSATISFIED |
  DISTRACTOR_FAILURE | INVALID_QUESTION`.
- **AC-15**: Given a `Question` value, when its keys are enumerated, then they are exactly
  `templateId`, `skill`, `text`, `params`, `choices`, `correctIndex`, `isWordProblem`,
  `readAloud` — no more, no fewer. `isWordProblem` and `readAloud` are typed `boolean`, not
  `boolean | undefined`, so a consumer never needs a truthiness guard. The test asserts the
  exactness with a `// @ts-expect-error` on both an excess property and a missing one.
- **AC-16**: Given a `Choice` value, when its keys are enumerated, then they are exactly `value`
  (a `number`) and `label` (a `string`) — no more, no fewer, asserted in the same
  `// @ts-expect-error` style.
- **AC-17**: Given a template object carrying `difficulty: 2`, when parsed, then `safeParse`
  returns `success: true` and `difficulty` is `2`; given `difficulty: 0` or `difficulty: 4`,
  then `safeParse` returns `success: false`; given the key absent, then `safeParse` succeeds and
  the key is **omitted** from the parsed object (not set to `undefined`).
- **AC-18**: Given a valid crew object `{ id, displayName, role }`, when parsed by `crewSchema`,
  then `safeParse` returns `success: true` and all three fields round-trip; given an object
  missing `role`, or with a non-string `role`, then `safeParse` returns `success: false`.
  *(Added by the orchestrator 2026-07-27: `crewSchema` was in the required-shapes block with no
  acceptance criterion, and T-006 authors `crew.json` against it while unable to edit
  `schemas.ts`. An unvalidated schema in a frozen file is a downstream trap.)*
- **AC-19**: Given any content object carrying an **unknown extra key** (e.g. a typo'd
  `recoilDmg` alongside the required fields), when parsed by `templateSchema`, `cannonSchema`,
  `skillSchema`, `islandSchema`, `rankSchema`, or `crewSchema`, then `safeParse` returns
  `success: false` — the schemas reject unknown keys rather than silently stripping them.
  *(Added by the orchestrator 2026-07-27. zod's default behaviour strips unknown keys, so a
  typo'd OPTIONAL field in a content catalog would validate cleanly and vanish — the catalog
  would look valid while silently losing data. ARCHITECTURE.md §4.4 requires catalogs to be
  "all typed, all zod-validated"; strictness is what makes that guarantee real. This is a
  content-correctness gate, and content correctness is what §9.1 calls the catastrophe class.)*

  ordering, discriminated `unlock`).

  stops a thinner shape being frozen here and blocking T-007 two waves later.

- Eval: none — schemas and types are deterministic.
