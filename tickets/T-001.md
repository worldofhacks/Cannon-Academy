## Context

This is the root of every random decision in the game: question parameters, distractor
shuffles, damage rolls, chest rarity, and bot behaviour all draw from here. `Math.random()`
and `Date` are lint-banned inside `src/engine/**` precisely so that this module is the only
source of nondeterminism, and so a duel can be replayed from a seed (ARCHITECTURE.md §4.2).

**The API must be pure and state-threaded, not a stateful closure.** `DuelState` carries the
PRNG state as an ordinary serialisable field so that the duel reducer stays a pure
`(state, event) => state` function and `DuelState` survives a JSON round-trip. A closure-based
generator cannot be serialised, which would break mid-duel save/relaunch (PLAN.md MVP
checklist: "kill the app mid-duel, relaunch, land safely on the map with progress intact").

This ticket has no dependencies. Downstream consumers: T-005, T-007, T-008, T-009, T-021.

**Reference algorithm (mulberry32) — implement exactly this:**

```
step(a: uint32):
  a = (a + 0x6D2B79F5) | 0
  t = Math.imul(a ^ (a >>> 15), 1 | a)
  t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t
  output = ((t ^ (t >>> 14)) >>> 0) / 4294967296
  nextState = a
```

## Planning Decisions

- `locked-decision` (orchestrator, 2026-07-27) — Pure state-threaded API returning
  `[value, nextRng]` tuples. ARCHITECTURE.md names mulberry32 and "seed carried in state" but
  does not fix an API shape; tuple-threading is chosen because it is serialisable and composes
  into the reducer. **Locked rather than left `proposed` because T-005, T-007, T-008, T-009 and
  T-021 all couple to this shape; a hedged interface in wave 1 is a frozen-test collision later
  (see LESSONS.md L-004).**
- `locked-decision` (orchestrator, 2026-07-27) — `Rng` is `{ readonly state: number }` (a boxed
  uint32), not a bare number, so a raw seed can never be passed where a live generator is expected.
- `locked-decision` (orchestrator, 2026-07-27) — **A weighted entry is
  `{ item: T; weight: number }`.** The field is `item`, NOT `value`. T-009 already declares
  `CHEST_RARITY_ENTRIES: readonly { item: ChestRarity; weight: number }[]`, so `item` is the
  binding name across the run.
- `locked-decision` — mulberry32 specifically (ARCHITECTURE.md §4.1 names it).

## Acceptance Criteria

- **AC-1**: Given a seed `s`, when `createRng(s)` is called twice and each result is advanced
  1,000 times with `nextFloat`, then the two output sequences are element-wise identical.
- **AC-2**: Given `createRng(1)` and `createRng(2)`, when each is advanced 10 times with
  `nextFloat`, then at least one output differs between the two sequences.
- **AC-3**: Given the reference mulberry32 pseudocode in Context re-implemented independently
  inside the test file, when `createRng(seed)` is advanced 100 times for each of the seeds
  `0`, `1`, `42`, `4294967295`, then every value from `nextFloat` equals the reference
  implementation's corresponding value exactly (`===`, no tolerance).
- **AC-4**: Given any seed, when `nextFloat` is drawn 100,000 times from `createRng(12345)`,
  then every value satisfies `0 <= v < 1`, and the arithmetic mean is within `[0.49, 0.51]`.
- **AC-5**: Given `nextInt(rng, min, max)`, when drawn 60,000 times from `createRng(777)` with
  `min = 1, max = 6`, then every value is an integer in `[1, 6]` inclusive and each of the six
  values occurs at least 9,000 and at most 11,000 times.
- **AC-6**: Given `nextInt(rng, 5, 5)`, when called, then it returns exactly `5` and the
  returned `Rng` is still advanced (its `state` differs from the input `Rng`'s `state`).
- **AC-7**: Given `nextInt(rng, min, max)` with `min > max` or with a non-integer `min` or
  `max`, when called, then it throws a `RangeError`.
- **AC-8**: Given `shuffle(rng, items)` on a 10-element array, when called, then the result is
  a new array (input not mutated, `!==` the input) that is a permutation of the input (same
  multiset), and over 10,000 shuffles from `createRng(99)` every one of the 10 elements
  appears in index 0 at least 700 and at most 1,300 times, **and the same band holds at a
  second index (index 5)**; and given a **4-element array shuffled 24,000 times** threaded from
  `createRng(99)`, then **all 24 permutations are observed** and each permutation's count is
  between 850 and 1,150.
  *(Full-permutation clause added by the orchestrator 2026-07-27. The index-0-only band was
  passed by a "shuffle" that swaps index 0 with one random position and leaves positions 1–9 in
  their original order (measured 946–1050 at index 0, but 0–8987 across all indices), and also
  by the classic biased n-pass swap (734–1281 — inside the band by 34 counts). T-007 uses
  `shuffle` to place the correct answer among the four choices, so a biased shuffle makes the
  answer's slot predictable and a child learns the position instead of the math — the
  "game teaches wrong math" catastrophe class in ARCHITECTURE.md §9.1. Verified: all four legal
  Fisher-Yates variants score 923–1057 on the new band; both biased implementations fail it.)*
- **AC-9**: Given `pick(rng, items)` on an empty array, when called, then it throws a
  `RangeError`; given a single-element array, then it returns that element; and given a
  **10-element array drawn 10,000 times** with the returned `Rng` threaded forward from
  `createRng(5)`, then every element is selected between 900 and 1,100 times, and the returned
  value is a `[value, nextRng]` tuple whose `nextRng` differs from the input.
  *(Uniformity clause added by the orchestrator 2026-07-27. The original criterion was satisfied
  by `pick = items[0]`, and by a `pick` returning a bare value rather than a tuple. T-007 uses
  `pick` to choose the question template from a pool of up to 8 — a constant `pick` means every
  question in the game comes from the same template — and T-021 uses it for the bot's cannon
  choice.)*
- **AC-10**: Given `weightedPick(rng, entries)` where each entry is `{ item: T; weight: number }`
  — the field is `item`, not `value` — with entries `[{item:'a',weight:1},{item:'b',weight:3}]`, when drawn 20,000
  times from `createRng(2026)`, then `b` is selected between 14,000 and 16,000 times, and `a`
  and `b` are the only values returned.
- **AC-11**: Given `weightedPick` with an empty entry list, or with any weight `< 0`, or with a
  total weight of `0`, when called, then it throws a `RangeError`. Given entries where **one
  weight is `0` alongside at least one positive weight** (`[{item:'z',weight:0},{item:'p',weight:1}]`),
  it does **not** throw, and across 5,000 threaded draws the zero-weight item is **never**
  selected.
  *(Zero-among-positive clause added by the orchestrator 2026-07-27. Previously unspecified, so
  an implementation that threw on any zero weight and one that could select the zero-weight item
  both passed. T-009 builds `CHEST_RARITY_ENTRIES` from `CHEST_RARITY_WEIGHTS` in `tuning.ts`,
  where a rarity weight of 0 is a legal way to disable a tier — so this would have surfaced in
  wave 3 as either a crash or a silently-awarded disabled rarity.)*
- **AC-13**: Given any of `nextFloat`, `nextInt`, `shuffle`, `pick`, and `weightedPick`, when the
  same un-reassigned `Rng` is passed to it twice, then both calls return an identical value and
  an identical (`toEqual`) `nextRng`, and the input `Rng`'s `state` is unchanged. No export
  returns or closes over hidden state.
  *(Added by the orchestrator 2026-07-27. Repeat-call purity was asserted for `nextFloat` only.
  A `nextInt` that advances the `Rng` correctly but derives its VALUE from a module-scoped
  counter scored a perfect [10000×6] on AC-5 and passed every other test in the suite — while
  making draws a function of process history rather than of the serialised seed. That destroys
  replay-from-{seed, action log} after a relaunch, which is the entire reason this module
  exists (ARCHITECTURE.md §4.2).)*
- **AC-14**: Given `shuffle`, `pick`, and `weightedPick`, then each accepts a `readonly` array
  without a type error.
  *(Added by the orchestrator 2026-07-27. Every test fixture was a mutable array, so nothing
  forced `readonly` parameter types — but T-009 passes `readonly { item; weight }[]`, T-007 a
  pool derived from `readonly Template[]`, and T-021 `readonly CannonId[]`. Mutable parameter
  types would compile here and fail three downstream tickets two waves later against a frozen
  contract.)*
- **AC-12**: Given any `Rng` value, when it is round-tripped through `JSON.parse(JSON.stringify(rng))`,
  then advancing the round-tripped value produces the same sequence as advancing the original.

## Test Plan

- Unit (deterministic): AC-1, AC-2 — reproducibility and seed sensitivity.
- Unit (deterministic): AC-3 — known-answer test against an in-test reference implementation
  written from the Context pseudocode. This is the anti-drift test; it is not circular because
  the test's reference is written from the spec, not from the implementation.
- Unit (deterministic): AC-4, AC-5, AC-8, AC-10 — fixed-seed distribution bounds. Deterministic
  because the seed is fixed; the bounds are loose enough to be stable, tight enough to catch a
  broken derivation.
- Unit (deterministic): AC-6, AC-7, AC-9, AC-11 — boundary and error cases.
- Unit (deterministic): AC-12 — serialisability.
- Eval: none. This module is a pure function; there is no LLM in this codebase.
