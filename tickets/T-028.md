## Context

After the wave-2 merge, `CHOICE_COUNT = 4` exists twice:

- `src/engine/tuning.ts:120` — exported (T-004, which claims the constant for `tuning.ts`)
- `src/engine/questions/types.ts:44` — a module-local `const` used by `assertQuestion` (T-003)

**Neither ticket is at fault.** T-003 was written before `tuning.ts` existed and was correct at the
time; T-004 correctly claimed the constant. **The merge creates the duplication**, and no scheduled
ticket collapses it — T-005 and T-007 both consume the `tuning.ts` copy, so the shadow persists.

**Why it matters despite both values being `4`.** ARCHITECTURE §4.3's stated purpose for
`tuning.ts` is that the hidden dev screen exposes these constants as **sliders**, so day-5 balance
tuning needs no rebuild. Move `CHOICE_COUNT` there and `assertQuestion` keeps validating against a
stale literal — every generated question then fails with `INVALID_QUESTION`. The failure is total,
immediate, and points at the wrong file.

This is not a live defect today. It is a trap armed for the first person who uses the feature the
architecture built `tuning.ts` for.

## Planning Decisions

- `proposed` — `types.ts` imports `CHOICE_COUNT` from `@engine/tuning` and deletes its local copy.
  This is the smaller change and matches §4.3's one-file rule literally.
- `open-question` — **the alternative is worth considering and is the owner's call:** `CHOICE_COUNT`
  may not be a _tuning_ constant at all. The four-choice grid is structural — the UI is a 2×2
  layout, K-friendly by design, and PLAN.md calls four-choice input "a deliberate call" rather
  than a tunable. A slider that breaks every question if moved is not a slider. If that reading is
  accepted, the fix is instead to remove `CHOICE_COUNT` from `tuning.ts`, keep it beside
  `assertQuestion` as a design invariant, and note in `tuning.ts` why it is deliberately absent.
  **Resolve this before implementing** — the two fixes move the constant in opposite directions.

## Acceptance Criteria

- **AC-1**: Given the merged tree, when `CHOICE_COUNT` is searched for across `src/`, then exactly
  one declaration exists.
- **AC-2**: Given `assertQuestion`, when it validates a question's choice count, then the value it
  compares against is the same declaration every other consumer reads — changing that one
  declaration changes `assertQuestion`'s behaviour.
- **AC-3**: Given a question with a number of choices equal to the single declared `CHOICE_COUNT`,
  then `assertQuestion` accepts it; given one more or one fewer, then it throws
  `QuestionGenerationError` with code `INVALID_QUESTION`.
- **AC-4**: Given the full repo suite, then it passes unchanged — this ticket removes a
  duplication and changes no behaviour at the shipped value.
